# 兼容性检查单

> 核心问题：换台机器、换个系统、升个版本、来个新用户——还能跑吗？
>
> 优先级说明：🔴 不做会丢数据/系统崩溃 | 🟡 不做有隐患 | 🟢 锦上添花

---

## 兼容性维度

```
平台兼容  → macOS / Linux / Windows
版本兼容  → Python 3.9 / 3.10 / 3.11 / 3.12
数据兼容  → 老版本的数据在新版本能读
接口兼容  → 改 API 不破坏现有调用方
配置兼容  → 老配置在新版本不报错
编码兼容  → 任何语言、任何平台都能正确显示
依赖兼容  → 依赖库升级不破坏现有功能
发布兼容  → 新版本如何安全地替换旧版本
```

## 开工前（设计阶段）

- [ ] 🔴 **Python 版本声明**：最低支持哪个版本？用了 3.10+ 才有的语法吗（如 `str | None`）？**不做的代价：用户 Python 3.9 直接报 SyntaxError，安装都过不了。**
- [ ] 🔴 **OS 差异处理**：路径用 `pathlib.Path`，换行用 `\n`，文件操作写死 `encoding="utf-8"`
- [ ] 🔴 **路径相对化**：`Path(__file__).resolve().parent.parent` — 不写死绝对路径
- [ ] 🔴 **配置文件向后兼容**：新字段有默认值，旧配置不报错
- [ ] 🟡 **Schema 版本化**：DB Schema 有版本号吗？怎么知道当前数据是哪个版本？
- [ ] 🟡 **依赖版本锁定**：`requirements.txt` 钉了版本号吗？
- [ ] 🟡 **Feature Flag 设计**：高风险功能是否用 flag 控制开关，而不是靠部署？**好处：出问题关 flag 即可，不需要回滚整个版本。不做的代价：小功能的 bug 需要全量回滚。**
- [ ] 🟢 **金丝雀发布策略**：新版本是 100% 全量替换，还是 1%→10%→50%→100% 渐进？**不做的代价：新版本的 bug 影响 100% 用户。**（MIND 是本地工具，金丝雀不适用；做 SaaS 时要有这个意识。）

## 上线前（验证阶段）

- [ ] 🔴 **多平台测试**：至少在 macOS + Linux 上都跑过
- [ ] 🔴 **多 Python 版本测试**：最低和最高支持的版本都测了
- [ ] 🔴 **旧数据迁移测试**：拿老备份在新版上正常读写
- [ ] 🔴 **新环境从零测试**：克隆 → install → 跑通，流程完整
- [ ] 🟡 **依赖升级测试**：`pip install --upgrade` 全部依赖后还能跑吗？
- [ ] 🟡 **破坏性变更通知**：不兼容改动通知到所有调用方了吗？有迁移指南吗？
- [ ] 🟡 **Feature Flag 切换测试**：flag 开/关状态都测过吗？切换后行为对吗？

## 可移植性快速扫描

```bash
# 硬编码绝对路径？
grep -rn "/Users/" --include="*.py"
# 平台特定命令？
grep -rn "os.system\|subprocess.*shell" --include="*.py"
# 文件操作无 encoding？
grep -rn "open(" --include="*.py" | grep -v "encoding"
# 字符串拼路径？
grep -rn "+ .*\/" --include="*.py"
```

## 常见翻车

| 翻车现场 | 原因 | 怎么防 | 级别 |
|---------|------|--------|------|
| Windows 路径报错 | 硬编码 `/` | 永远用 `pathlib.Path` | 🔴 |
| Mac 能跑 Linux 报错 | 文件名大小写 | 统一小写或保持严格一致 | 🔴 |
| 升级后配置报错 | 新字段没默认值 | 新配置字段必须有默认值 | 🔴 |
| 小功能 bug 被迫全量回滚 | 无 feature flag | 高风险功能用 flag 包裹，出问题关 flag | 🟡 |
| 依赖版本冲突 | 没锁版本 | `requirements.txt` 钉版本号 | 🟡 |
| `str | None` 在 3.9 报错 | 用了 3.10+ 语法 | README 声明最低版本要求 | 🟡 |

## 反例（来自 MIND）

- ✅ `BASE_DIR = Path(__file__).resolve().parent.parent` — 可移植典范
- ✅ `expanduser("~/.claude/projects")` — 跨用户
- 🔴 用 `str | None` 语法（3.10+）但未在 README 声明最低版本
- 🟡 依赖 `requests` 没有钉版本
- 🟡 无 feature flag 机制 — 所有改动直接生效，出问题只能回滚

## 底层原理：换机器换版本还能跑吗

### 向前兼容 vs 向后兼容：新旧版本谁迁就谁

**两个方向的兼容**，很多人混为一谈：

| | 向后兼容（向下兼容） | 向前兼容（向上兼容） |
|---|-------------------|-------------------|
| 含义 | 新版本能读旧版本的数据/配置/调用 | 旧版本能读新版本的东西 |
| 通俗理解 | 升级后旧东西还能用 | 老程序能预览新文件 |
| 例子 | Python 3.x 能跑 2.x 的大部分代码 | 老浏览器能渲染新 HTML 标签 |
| 难易 | 较容易，是默认要求 | 很难，几乎无法保证 |

**工程含义**：现实中我们承诺的是**向后兼容**——新版本必须能处理旧版本产生的东西（老配置、老数据、老调用方）。向前兼容基本不可实现，只能尽力（Postel 法则，见下）。

### SemVer：版本号的约束逻辑

**核心思路**：`MAJOR.MINOR.PATCH` 不只是数数，而是给调用方一个**契约承诺**：

| 位 | 变化意味着 | 调用方该怎么办 |
|----|-----------|---------------|
| MAJOR | 破坏性变更（接口/数据格式变了） | 不升级就坏，必须测试 |
| MINOR | 加了新功能（向后兼容） | 可以放心升 |
| PATCH | 修 bug（向后兼容） | 闭眼升 |

**关键约束**：**破坏性变更必须升 MAJOR**，否则就是违约。调用方依赖"版本号语义"来决定是否升级——你违反了这个约定，别人就会踩坑。

**洞察**：检查单"破坏性变更通知、迁移指南"——底层就是 SemVer 的契约精神：版本号是给调用方的承诺，不是给你自己的记事本。

### Postel 法则：发送要严格，接收要宽容

**原文**："Be liberal in what you accept, and conservative in what you send."

**两层含义**：
- **接收宽容**：处理别人的输入时，容忍格式的细微偏差（多余空格、大小写、缺失可选字段），不轻易拒绝
- **发送严格**：自己产出时，严格遵循标准格式，不产生让别人为难的怪输出

**为什么冲突**：检查单"输入校验要严格拒绝"（安全）和 Postel 的"接收宽容"看起来矛盾。答案：**安全边界要严格，同生态内的兼容要宽容**。对不可信的外部输入严格校验（防注入），对自己上下游的格式偏差宽容（防兼容性崩坏）。

### 三层兼容：数据 / 配置 / 接口 独立评估

**核心认知**：兼容性不是一件事，是三件事——数据、配置、接口，各自独立地可能不兼容：

| 层 | 不兼容的表现 | 怎么防 |
|----|-------------|--------|
| **数据兼容** | 老数据库新代码读不了 | Schema 版本化 + 迁移脚本 |
| **配置兼容** | 老配置文件新代码报错 | 新字段给默认值，旧字段保留 |
| **接口兼容** | 老调用方调新代码崩 | 加新参数保留旧参数，不删旧行为 |

**洞察**：升级一次，三个层各自要评估。只测了数据层忘了配置层 → 老用户升级就崩。检查单把"老数据迁移测试""配置向后兼容""接口向后兼容"分开列——因为它们是三个独立的风险点。

## 工程实践手段

| 原理 | 落地动作 |
|------|---------|
| 向后兼容 | 加新字段带默认值；旧参数保留过渡期；破坏性变更升 MAJOR |
| SemVer | 版本号语义化；README 声明最低 Python 版本；changelog 记录 |
| Postel | 对外严格校验（Pydantic），对内宽容解析 |
| 数据兼容 | Alembic 版本化迁移 + 老备份在新版上读写测试 |
| 配置兼容 | 新配置字段有默认值，缺失不报错 |
| 接口兼容 | 加参数不删参数；废弃接口给日落时间 + 替代提示 |
| feature flag | 高风险功能用 flag 包裹，出问题关 flag 不回滚 |
| 金丝雀 | 1%→10%→50%→100% 渐进（SaaS 场景） |
| 多平台 | CI 跑 macOS + Linux 矩阵 + 最低/最高 Python 版本 |

## 推荐开源项目（跨语言）

| 项目 | 语言 | 定位 | 优势 | 劣势 / 风险 | 适用场景 |
|------|------|------|------|------------|---------|
| **Docker** | Go | 环境标准化 | 跨平台可复现、分发一致、CI 同环境 | 资源开销、macOS 慢（VM） | 打包/分发/CI |
| **GitHub Actions** | — | CI/CD | 矩阵矩阵测试、与仓库集成、市场丰富 | 免费额度有限、自托管要运维 | 多平台 CI 矩阵 |
| **pyenv** | Shell | 多 Python 版本 | 简单、按目录切版本 | Python only | 多版本测试 |
| **nvm** | Shell | 多 Node 版本 | 简单、生态标准 | Node only | 多版本测试 |
| **tox** | Python | 多环境测试矩阵 | 自动建 env、矩阵化 | Python only | Python 兼容性 CI |
| **Hatch** | Python | 工程化 | 现代、打包+环境一体 | 较新 | 新 Python 项目 |
| **Renovate** | TypeScript | 依赖自动更新 | 自动提 PR、group、可定制 | PR 噪音多需过滤 | 依赖版本维护 |
| **Dependabot** | — | 依赖自动更新 | GitHub 原生、零配置 | 定制弱 | 依赖更新起步 |

**选型建议**：Docker 保证"换个机器一样跑"；CI 用 GitHub Actions 跑多平台矩阵；多 Python 版本用 pyenv/tox。依赖更新交给 Renovate 自动 PR，重点看 breaking 变更。
