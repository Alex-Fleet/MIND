# 测试检查单

> 核心问题：你怎么知道代码是对的？改了一行，怎么知道没把别处弄坏？
>
> 优先级说明：🔴 不做会丢数据/系统崩溃 | 🟡 不做有隐患 | 🟢 锦上添花

---

## 测试金字塔

```
         ╱  E2E  ╲         少量，慢，验证核心用户流程
        ╱ 集成测试 ╲        中等，中速，验证模块间协作
       ╱   单元测试   ╲      大量，快，验证单个函数行为
```

## 开工前（设计阶段）

- [ ] 🔴 **测试策略**：哪些单测？哪些集成？哪些 E2E？覆盖率目标？**不做的代价：改代码靠运气，出了 bug 用户告诉你。**
- [ ] 🔴 **可测试性**：函数副作用太多了吗？依赖能注入吗？状态能重置吗？
- [ ] 🟡 **测试数据**：用的是真实数据还是 mock？mock 太假会测不出问题
- [ ] 🟡 **Contract Testing 意识**：如果你的 API 被外部调用，改接口时怎么知道没破坏下游？**PACT 等 contract testing 工具验证 Provider 和 Consumer 之间的契约。不做的代价：你改了 API 返回格式，下游全炸，你还不知道。**

## 每个函数必须覆盖

```
□ 正常输入 → 预期输出
□ 空值/None → 不崩、返回合理默认值或清晰报错
□ 零值/负值 → 不崩、行为明确
□ 边界最大值 → 不崩、结果正确
□ 超长输入 → 截断还是拒绝？不崩
□ 非法字符 → 拒绝还是清洗？不崩
□ 并发调用 → 数据不竞争、结果一致
□ 依赖失败 → 降级还是报错？行为明确
□ 写入后读回 → 数据一致
```

## 上线前（验证阶段）

- [ ] 🔴 **全量测试通过**：所有绿色再部署
- [ ] 🔴 **回归测试**：改动的间接影响确认了吗？相关模块测试跑了？
- [ ] 🔴 **flaky test 清零**：有时过有时不过的测试 = 等于没测
- [ ] 🟡 **真实数据测试**：用了生产数据（脱敏后）测过吗？不只是 mock
- [ ] 🟡 **容量测试**：1000 条能跑，100000 条呢？
- [ ] 🟢 **Chaos Engineering**：主动注入故障（杀进程、断网络、磁盘满）→ 系统表现符合预期吗？**目的：验证韧性假设，不是等生产帮你测。不做的代价：你以为的"容错"从来没真测过，第一次真故障就是你最需要它的时候。**

## 测试反模式（绝对不要）

```
❌ 针对测试用例走捷径        → 测试是照妖镜不是门面
❌ 写测试只为覆盖率          → 无断言的测试 = 废纸
❌ mock 一切                 → 关键路径用真实依赖
❌ "太小了不用测"            → 小函数藏着边界 Bug 概率不小
❌ 修 bug 不加测试            → 同样的 bug 会再来一次
❌ 测试代码质量差             → 测试也是代码，也要可读可维护
❌ "我手动测过了"             → 手动不可靠不可重复，自动化
```

## 常见翻车

| 翻车现场 | 原因 | 怎么防 | 级别 |
|---------|------|--------|------|
| 只测 happy path | 没想到边界 | 强制要求每个函数至少一个异常路径用例 | 🔴 |
| 测试依赖执行顺序 | 共享状态 | 每个测试独立 setUp/tearDown | 🔴 |
| mock 太多测不到真实问题 | 假数据太假 | 关键路径必须有集成测试 | 🔴 |
| flaky test 被忽略 | "再跑一次就过了" | flaky = 有 bug，修测试或修代码 | 🔴 |
| 测试自己 bug 假绿 | 测试逻辑写错 | Code review 测试码和产品码同等严格 | 🟡 |
| 改了 API 下游炸了才知道 | 无 contract test | PACT 验证 Provider-Consumer 契约 | 🟡 |
| 容错代码从来没真测过 | 只在脑子里假设"这个能容错" | Chaos engineering：主动注入故障验证 | 🟢 |

## 反例（来自 MIND）

- 🔴 目前基本无自动化测试 — 所有验证靠手动
- 🔴 `store.py` CRUD 无单测 — 改 SQL 靠肉眼检查
- 🔴 `inject.py` 输出正确性无自动化验证 — 每次手动 `wc -c`
- 🔴 "子代理跑测试"铁律写了但项目里没有可跑的测试
- 🟡 改 API 无 contract test — 看板前端手动对照

## 底层原理：怎么知道代码是对的

### 测试金字塔：为什么是金字塔的形状

**核心问题**：测试成本不同，该怎么分配数量？

```
         ╱  E2E  ╲        少量（慢、贵、端到端，一次跑几分钟）
        ╱ 集成测试 ╲       中等（中速，验证模块间协作）
       ╱   单元测试   ╲      大量（快、便宜、毫秒级）
```

**数学逻辑**：测试的**价值 = 捕获 bug 的能力 ÷ 成本**。
- 单元测试：毫秒级、便宜、每次改动全量跑 → 用大量
- E2E 测试：几分钟、贵、覆盖用户主流程但一崩全崩 → 用少量
- 集成测试居中

**洞察**：金字塔不是偏好是**成本效益分析**。把 E2E 写得比单元测试多 = 每次跑测试要 10 分钟，开发反馈循环被拖死。测试太少 = 靠感觉验证。平衡点是大部分单元 + 少量关键 E2E。

### 确定性：为什么测试必须可重复

**核心问题**：测试两次结果不同（flaky test）——上次绿这次红，这个测试还有用吗？

**答案**：flaky test = 有 bug。它揭示了两种问题之一：
1. **测试本身有 bug**：依赖执行顺序、共享状态、依赖真实时钟/网络/随机数
2. **被测代码有竞态**：真正的并发 bug，只是多数时候碰巧没触发

**洞察**：检查单"flaky 清零"的底层逻辑——不可重复的测试没有信息量。它绿了你不放心，红了你不知道是不是真坏了。**一个 flaky test 比没有测试更糟**，因为它消耗信任。

### 属性测试的数学原理：反例收缩

**核心问题**：用例测试（unit test）的边界是你自己想的——你只会写你想到的输入。隐藏的 bug 往往在你想不到的输入上。

**属性测试（Property-Based Testing，如 Hypothesis）的思路**：
1. 你描述"对所有输入都应成立的性质"（如 `decode(encode(x)) == x`）
2. 工具自动生成海量输入（空串、emoji、超长串、null 字节、负数…）
3. 找到违反性质的输入后，**自动收缩（Shrinking）**——把反例逐渐简化成最小的复现（"这个 1000 字节的输入能复现，试试 3 个字节呢？…找到了，`\x00` 就行"）

**洞察**：收缩是关键创新——它把"随机发现的失败"变成"可读的最小复现"，像把指纹还原成地址。用例测试靠你的想象力，属性测试不靠。

### 覆盖率 ≠ 正确性

**核心认知**：100% 覆盖率只能证明"这行代码被执行过"，不能证明"它执行对了"。

```
if a:
    return b    # 这行被跑了，但断言是什么？
    # 没断言的覆盖 = 跑了等于没跑
```

**覆盖率的正确用法**：
- 用它**发现未覆盖的代码**（红区 = 潜在未测 bug 区）
- 不用它**当作质量门**（为了 100% 覆盖写无断言测试，是作弊）

**洞察**：检查单"写测试只为覆盖率 = 废纸"——底层就是覆盖率度量的是"代码走了多少"，不是"正确性被验证了多少"。

### 依赖注入：怎么让代码可测

**核心问题**：一个函数直接调 `requests.get()` 或 `sqlite3.connect()`——测试时没法换假依赖，只能测真的（慢、有外部副作用）。

**依赖注入（DI）的本质**：把"用什么依赖"从函数内部挪到调用方传入。

```
不好：def ingest():  db = sqlite3.connect(...)   # 测试绕不开真 DB
好：   def ingest(db):  ...                       # 测试传假 DB
```

**洞察**：检查单"依赖能注入吗？状态能重置吗？"——底层是可测试性。依赖注入让测试能在**边界**（DB、网络、时间）处放假的，而业务逻辑本身用真的。这比 mock 一切可靠（见翻车表"mock 太多测不到真实问题"）。

## 工程实践手段

| 原理 | 落地动作 |
|------|---------|
| 金字塔 | 大量单元 + 中等集成 + 少量 E2E；E2E 只覆盖主流程 |
| 确定性 | 测试独立 setUp/tearDown；mock 掉时钟/网络/随机数；flaky 一律修 |
| 属性测试 | hypothesis：对核心纯函数写性质（round-trip、不变量），自动收缩 |
| 覆盖率 | coverage.py + pytest-cov 当"雷达"找盲区，不当"门禁" |
| 依赖注入 | 依赖从参数传入；边界放 mock（pytest-mock），业务用真依赖 |
| Contract | 对外 API 用 PACT 验证 Provider-Consumer 契约 |
| Chaos | 关键容错路径主动注入故障（杀进程/断网/磁盘满）验证 |

## 推荐开源项目（跨语言）

| 项目 | 语言 | 定位 | 优势 | 劣势 / 风险 | 适用场景 |
|------|------|------|------|------------|---------|
| **pytest** | Python | 单元/集成 | fixture 注入、插件生态、并行 | Python only | Python 测试地基 |
| **Jest** | Node/TS | 单元/集成 | 内置 mock+快照+覆盖率 | 绑定 Node | JS/TS 项目 |
| **Go test** | Go | 单元/集成 | 标准库内置、并行、benchmark | Go only | Go 项目 |
| **hypothesis** | Python | 属性测试 | 自动生成输入+反例收缩 | Python only | 纯函数不变量 |
| **fast-check** | TS | 属性测试 | TS 类型友好、快速 | JS 生态 | JS/TS 属性测试 |
| **pytest-mock** | Python | Mock | 与 pytest 集成、自动清理 | mock 过度风险 | 测试边界替身 |
| **Playwright** | JS/多 | E2E | 多浏览器、自动等待、多语言 | 重、浏览器二进制大 | 端到端主流程 |
| **Cypress** | JS | E2E | 调试体验、时间旅行 | 只跑自家浏览器 | 前端 E2E |
| **coverage.py / pytest-cov** | Python | 覆盖率 | HTML 报告、分支覆盖 | 不是正确性 | 找测试盲区 |
| **PACT** | 多语言 | 契约测试 | Provider/Consumer 各自独立测 | 生态成熟度不一 | API 消费者/提供者 |
| **Chaos Monkey** | Java | 混沌工程 | 生产注入故障 | 重、需护栏 | 大型系统韧性验证 |

**选型建议**：地基选 pytest（+ pytest-mock），纯函数加 hypothesis 找隐藏 bug，E2E 用 Playwright 只覆盖主流程。覆盖率当雷达不用作门禁。契约用 PACT（改 API 前先验契约）。
