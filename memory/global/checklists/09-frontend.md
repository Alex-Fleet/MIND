> 核心问题：任何设备、任何网络、任何操作下——还能用吗？
>
> 优先级说明：🔴 不做会丢数据/系统崩溃 | 🟡 不做有隐患 | 🟢 锦上添花

## 开工前（设计阶段）

- [ ] 🔴 **三种状态**：每个组件都有加载中 / 加载失败 / 数据为空三个状态的 UI 吗？**不做的代价：用户看到白屏或无限 spinner，以为你的产品坏了。**
- [ ] 🔴 **响应式设计**：320px（手机）→ 768px（平板）→ 1440px（桌面）都看过了吗？
- [ ] 🔴 **边界数据量**：1 条 vs 100 条 vs 10000 条 — 渲染会卡吗？需要虚拟滚动吗？
- [ ] 🔴 **乐观更新 vs 等待**：用户操作后立即更新 UI（乐观）还是等 API 返回？选的代价是什么？
- [ ] 🔴 **防重复提交**：按钮点击后 disable/防抖了吗？快速双击不会提交两次？
- [ ] 🟡 **浏览器兼容**：目标浏览器（Safari/Chrome/Firefox/Edge）都测过吗？
- [ ] 🟡 **CSS 防御**：长文本自动换行、flex gap 替代 margin、min-height 替代固定 height
- [ ] 🟡 **内存泄漏**：useEffect cleanup 写了吗？定时器/事件监听器清理了吗？
- [ ] 🟡 **a11y（无障碍）**：屏幕阅读器能读吗？键盘能操作吗？色盲用户能区分吗？**目标：WCAG 2.1 AA 级。不做的代价：在欧美市场可能面临法律诉讼，且排除残障用户群体。**
- [ ] 🟢 **PWA / 离线支持**：网络断开时用户看到什么？白屏？缓存页？离线提示？**不强求全离线，但至少要有降级 UI。不做的代价：用户在飞机/地铁上打开你的应用，看到的是浏览器恐龙游戏。**

## 前端性能专项

- [ ] 🔴 **首屏加载**：首次加载要多久？有没有 spinner 不给用户白屏？
- [ ] 🔴 **打包体积**：JS bundle 多大？路由级 code split？
- [ ] 🟡 **Core Web Vitals**：Google 的三项核心指标达标了吗？
  - **LCP（Largest Contentful Paint）**< 2.5s — 最大可见元素渲染时间
  - **INP（Interaction to Next Paint）**< 200ms — 用户交互响应延迟
  - **CLS（Cumulative Layout Shift）**< 0.1 — 页面视觉稳定性（别突然跳来跳去）
  - **不做的代价：Google 搜索排名下降，用户感觉"这个网站很慢"。**
- [ ] 🟡 **重渲染控制**：改一条导致全列表重渲染？`React.memo` / `useMemo` 用对了吗？
- [ ] 🟡 **网络失败**：API 失败是静默还是给用户反馈？有重试按钮吗？

## 底层原理：任何设备任何操作下还能用吗

### 虚拟 DOM / Reconciliation：为什么 setState 更新快

**核心问题**：数据变了，整个页面要重画吗？如果每次 setState 都重建全部 DOM——万条列表每改一条就全量重绘，卡死。

**虚拟 DOM 的思路**：
1. 数据变化 → 不直接碰真实 DOM，先在内存里用 JS 对象（虚拟 DOM）算一遍"更新后的样子"
2. **Diff（差异对比）**：把新旧两棵虚拟 DOM 树对比，算出**最小变更集**（哪几个节点变了）
3. 只把变更集应用到真实 DOM——其他节点不动

**为什么快**：真实 DOM 操作很贵（触发重排/重绘），而 JS 对象对比很便宜。用"便宜的对比"换来"最少的昂贵操作"。

**React 的优化手段**：`React.memo` / `useMemo` / `key`——本质是减少 diff 的对比范围。**`key` 给 diff 提供身份信息**：列表项有稳定 key，React 才知道"这条是移动了，不是删了重建"。这就是检查单"过滤后列表不变"（同引用没触发更新）和"key 要正确"的底层原因。

### 浏览器渲染管线：Layout → Paint → Composite

**核心流程**：浏览器把 DOM 变成屏幕上的像素，要过这几关：

```
Style（算样式） → Layout（算位置大小） → Paint（画像素） → Composite（合成图层）
```

**每个操作的开销不同**：
- 改 `transform`/`opacity` → 只需 **Composite**（快，GPU 合成）
- 改 `width`/`height`/`top` → 触发 **Layout**（慢，要重排全部相关元素）
- 改 `color`/`background` → 触发 **Paint**（中，重绘）

**洞察**：检查单"改一条导致全列表重渲染"——底层是渲染管线的哪一层被触发了。动画用 `transform`（合成层）而不是 `top/left`（布局层），就是让 GPU 干活而不是 CPU 重排。

### 事件循环与防抖节流：为什么高频事件要限速

**核心问题**：滚动、输入、resize 这些事件一秒钟触发几十上百次。每次都处理（发请求、重算布局）→ 疯狂浪费。

| | 防抖 Debounce | 节流 Throttle |
|---|--------------|--------------|
| 行为 | 停止触发后才执行（等安静） | 固定频率执行（最多 N 次/秒） |
| 例 | 搜索输入框（停 300ms 才搜） | 滚动位置保存（每 200ms 一次） |
| 何时用 | 最终结果才重要 | 持续过程也要反馈 |

**洞察**：检查单"防重复提交"的底层——防抖/节流是事件循环上的"限流"。双击提交按钮 = 两个请求 = 两份数据（如果接口不幂等）。提交后立刻 disable 按钮，是最简单的防抖。

### RAIL 模型：每类响应该多快

**Google 的性能目标框架**，四类交互各自的响应预算：

| 类别 | 目标 | 含义 |
|------|------|------|
| **R**esponse | < 100ms | 点击后 100ms 内有反馈（否则用户觉得没点中） |
| **A**nimation | 每帧 < 16ms | 动画 60fps（16.7ms/帧）不掉帧 |
| **I**dle | 有空闲 | 留出空闲时间处理异步（不要让主线程永远忙） |
| **L**oad | < 2.5s（LCP） | 首屏加载 2.5s 内看到主要内容 |

**洞察**：Core Web Vitals 的 LCP/INP/CLS 就是 RAIL 的可测量版本。检查单"首屏加载多快""spinner 不给白屏"——底层是 LCP（2.5s）和 Response（100ms）预算。

### 单向数据流：状态管理为什么这么设计

**核心问题**：多个组件共享同一份数据（如筛选状态、用户信息）。如果每个组件自己改自己的一份，改完互相不一致——显示全乱。

**单向数据流的约定**：

```
状态（单一来源） → 派生 → 视图（渲染） → 事件 → 改状态（唯一入口）
        ↑                                        │
        └──────── 重新渲染（循环但方向单一） ←────┘
```

**为什么单向**：数据只能从一个方向流动（状态 → 视图），修改只能通过显式事件回传。出了 bug 能追查"是谁改的"，而双向绑定会陷入"你改我我改你"的死循环。

**洞察**：MIND 看板从"全局 `S` 对象"迁移到 `useState`（07-27 日报）——底层就是把双向/共享可变状态改成单向数据流。这也是 Zustand/Redux 存在的理由。

## 工程实践手段

| 原理 | 落地动作 |
|------|---------|
| 虚拟 DOM | 列表加稳定 `key`；`React.memo`/`useMemo` 控制重渲染；不 mutate 原数据 |
| 渲染管线 | 动画用 `transform`/`opacity`（Composite）不用 `top/left`（Layout） |
| 防抖节流 | 搜索/滚动/输入用 debounce/throttle；提交后 disable 按钮 |
| RAIL | 目标：LCP<2.5s、INP<200ms、CLS<0.1，用 Lighthouse 审计 |
| 单向数据流 | 状态提升到单一来源；修改走显式事件；状态不散落 |
| 三态 + ErrorBoundary | 每个组件有 loading/error/empty 三态；报错有兜底不白屏 |
| 虚拟滚动 | react-window / @tanstack/virtual（万条数据不卡） |
| a11y | Tab 序 + focus ring + aria-label + 键盘可达，WCAG 2.1 AA |

## 推荐开源项目（跨语言）

| 项目 | 类型 | 定位 | 优势 | 劣势 / 风险 | 适用场景 |
|------|------|------|------|------------|---------|
| **React** | JS | UI 框架 | 生态最大、组件复用、React Native 同源 | 学习曲线、bundle 大 | 大型 SPA |
| **Vue** | JS | UI 框架 | 上手快、模板直观、生态好 | 生态略小于 React | 中小型 / 国内生态 |
| **Svelte** | JS | UI 框架 | 编译期、运行时零依赖、性能好 | 生态小、招人难 | 高性能轻量应用 |
| **Vite** | JS | 构建工具 | HMR 极快、原生 ESM、TS 友好 | 生态发展中 | 新项目默认选 |
| **Tailwind CSS** | CSS | 样式 | 设计约束、响应式、深色模式 | 类名污染 HTML | 快速 UI 一致 |
| **react-window** | JS | 虚拟滚动 | 轻量、只渲染可见区 | React only | 万条列表 |
| **@tanstack/virtual** | JS | 虚拟滚动 | 框架无关 | 较新 | 任意框架虚拟滚动 |
| **Zustand** | JS | 状态管理 | 极简、按需订阅、无 boilerplate | 大型复杂需评估 | 中小型状态 |
| **Pinia** | JS | 状态管理 | Vue 官方推荐 | Vue only | Vue 状态 |
| **dayjs** | JS | 日期 | 轻量、tree-shaking、多语言 | 功能少于 date-fns | 前端日期处理 |
| **Lighthouse** | JS | 性能审计 | Core Web Vitals、免费 | 本地 CLI 要配 | 上线前审计 |

**选型建议**：新项目 React/Vue + Vite + Tailwind；万条列表必须虚拟滚动（react-window）；状态中小型用 Zustand，别上 Redux 那套重家伙。上线前 Lighthouse 审计 LCP/CLS。
