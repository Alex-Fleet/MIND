# 资源管理与性能检查单

> 核心问题：内存、磁盘、连接——每个都是有限的。耗尽了怎么办？数据量翻 10 倍还能这么快吗？
>
> 优先级说明：🔴 不做会丢数据/系统崩溃 | 🟡 不做有隐患 | 🟢 锦上添花

---

## 资源类型与耗尽后果

| 资源 | 耗尽后果 | 管控手段 | 级别 |
|------|---------|---------|------|
| 内存 | OOM 被杀、系统卡死 | 流式处理、内存预算、及时释放 | 🔴 |
| 磁盘 | 写入失败、DB 损坏 | 容量监控、日志轮转、定期清理 | 🔴 |
| 文件句柄 | 打不开文件/socket | with/try-finally、连接池上限 | 🔴 |
| DB 连接 | 新请求排队超时 | 连接池、操作完立即归还 | 🔴 |
| API 配额 | 调用失败、超额扣费 | 速率限制、配额监控 | 🔴 |
| CPU | 请求堆积、雪崩 | 并行度控制、异步化 | 🟡 |

## 开工前（设计阶段）

- [ ] 🔴 **数据量预估**：现在多少条？一年后？十倍呢？设计心智能否覆盖目标量级？
- [ ] 🔴 **内存预算**：一次加载多少到内存？N=100 → 100KB 安全，N=1000000 → 1GB 需要流式。**不做的代价：OOM 进程被杀，用户看到的是突然崩溃。**
- [ ] 🔴 **流式 vs 全量**：大文件/大结果集用流式逐条处理，还是一次全加载？
- [ ] 🔴 **索引设计**：DB 查询的 WHERE 条件都有索引吗？跑过 `EXPLAIN QUERY PLAN` 吗？
- [ ] 🔴 **N+1 查询识别**：循环里有 DB 查询吗？"先查 1 条，循环里每条再查" = N+1 灾难
- [ ] 🔴 **连接池上限**：到达上限后行为是什么？等待/报错/扩容？
- [ ] 🟡 **数据结构选择**：`if x in list` O(n) / `if x in set` O(1) — 选对了吗？
- [ ] 🟡 **分页策略**：用 OFFSET 还是 keyset/cursor 分页？**OFFSET 在大数据量下越来越慢（数据库仍需扫描跳过的行），100 万条后 OFFSET 1000000 几乎不可用。用 `WHERE id > last_seen_id LIMIT N` 替代。**
- [ ] 🟡 **缓存淘汰策略**：缓存满了怎么办？TTL（按时间过期）？LRU（踢最久没用的）？大小上限？**不设上限的缓存 = 内存泄漏。不做的代价：内存被缓存占满，OOM。**
- [ ] 🟡 **清理策略**：临时文件、旧日志有自动清理吗？还是永久累积？

## 性能优化决策流

```
发现慢操作 → 测量实际耗时（profile/计时器/EXPLAIN）
    ├── DB 慢 → 加索引？优化 SQL？减少查询次数？批量操作？
    ├── 网络慢 → 并行？异步？缓存？减少请求体积？设超时？
    ├── 内存大 → 流式处理？释放不用对象？更紧凑数据结构？
    ├── CPU 高 → 更好的算法？减少重复计算？
    └── 磁盘慢 → 批量写入？异步写入？
    → 优化后重新测量 → 记录基线
```

## 上线前（验证阶段）

- [ ] 🔴 **长时间运行测试**：跑 1000 个操作后内存是否持续增长？（泄漏）
- [ ] 🔴 **文件句柄泄漏测试**：反复开关文件 10000 次，还能打开吗？
- [ ] 🔴 **缓存上限测试**：缓存装满后系统行为对吗？淘汰策略生效了吗？
- [ ] 🟡 **大输入测试**：喂 10 倍正常大小的输入 → 内存/磁盘变化？
- [ ] 🟡 **数据量扩展测试**：10K → 100K → 1M 条记录，关键操作耗时曲线？
- [ ] 🟡 **分页性能测试**：OFFSET 100000 → 耗时多少？keyset 分页对比呢？
- [ ] 🟡 **并发性能测试**：单用户快，10 个并发还快吗？
- [ ] 🟡 **最慢请求分析**：P99 延迟是多少？瓶颈在哪？
- [ ] 🟡 **磁盘增长规划**：按当前速率多久占满？有预警吗？

## 常见翻车

| 翻车现场 | 根因 | 修复 | 级别 |
|---------|------|------|------|
| 页面加载 5 秒 | N+1 查询：一次请求查了 50 次 DB | JOIN/IN 一次取完 | 🔴 |
| DB 越来越慢 | 缺索引→全表扫描 | `CREATE INDEX ON table(col)` | 🔴 |
| 内存持续增长直到 OOM | 大列表一直 append 不释放 / 缓存无限增长 | 流式处理 + 缓存设上限+淘汰策略 | 🔴 |
| 文件句柄耗尽 | 打开不关 | `with open()` / try-finally | 🔴 |
| 翻到第 100 页要 5 秒 | OFFSET 分页扫描所有跳过的行 | keyset/cursor 分页：`WHERE id > last_id LIMIT N` | 🟡 |
| 缓存占满内存 | 没设淘汰策略 | TTL + LRU + 大小上限，三者至少有一个 | 🟡 |
| Rust target/ 几十 GB | 编译产物不清理 | `cargo clean` | 🟡 |
| 日志无限增长占满磁盘 | 无轮转 | 按大小切割，保留最近 N 个 | 🟡 |

## 反例（来自 MIND）

- ✅ `get_turn_summaries_in_window()` 有 LIMIT 150 — 有分页意识
- 🟡 inject 一次拼 150 条 turn 到 48KB 字符串 — 数据翻倍时可能卡
- 🔴 看板轮询全量 5256 条 feed 无分页 — 每 12s 全量刷新
- 🟡 没有性能基线 — 不知道什么时候变慢了
- 🟡 没有 VACUUM 策略 — DB 211MB 还在涨

## 底层原理：有限的资源耗尽怎么办

### 大 O 复杂度：数据量翻倍，代价涨多少

**核心直觉**：同一个操作，数据量从 1 万涨到 10 万，开销怎么变？

| 复杂度 | 含义 | 数据量×10 后 | 例 |
|--------|------|-------------|-----|
| O(1) | 一次搞定 | 不变 | 哈希查找 |
| O(log n) | 每次排除一半 | +3 倍 | B+ Tree 查找 |
| O(n) | 扫一遍 | ×10 | 线性扫描 |
| O(n²) | 两两比较 | ×100 | 嵌套循环 |

**洞察**：性能翻车几乎都是"数据量涨了，但算法还是 O(n²)"。检查单"数据量翻 10 倍还能这么快吗"——底层就是在问：你的瓶颈算法是大 O 的哪一档？

### 内存层级：为什么"内存快"和"磁盘慢"差 5 个数量级

**硬件事实**（速度数量级，相对值）：

```
CPU 寄存器   ≈ 0.3ns     ← 闪电
L1 缓存      ≈ 1ns       ← 微光
L2 缓存      ≈ 3ns
RAM 内存     ≈ 100ns
SSD          ≈ 100μs     ← 慢 1000 倍
磁盘 HDD     ≈ 10ms      ← 慢 100000 倍
```

**洞察**：一次磁盘 IO 的时间足够 CPU 做几百万次运算。这就是为什么：
- 数据库要索引（减少磁盘读次数）
- 缓存有用（热点数据留在内存）
- 流式处理有用（不把整个大文件读进内存）

### B+ Tree：数据库索引的底层结构（从 01 归位过来）

**核心思路**：数据全在叶子节点，叶子节点之间用链表串起来。非叶子节点只存"路标"（key），不存数据。

**带来的好处**：
- **范围查询极快**：找到起点，顺着叶子链表往后扫。`WHERE id BETWEEN 100 AND 200` 定位到 100 后一路读过去。
- **树高恒定且矮**：每个节点塞几百个 key，树只有 3~4 层就能覆盖百万级数据。每次查询 = 3~4 次磁盘读（对应上面内存层级：省了 3~4 次磁盘 IO）。
- **为什么 `SELECT *` 慢**：二级索引叶子存的是主键，拿到主键还要回主索引再查一次拿整行（回表）。`EXPLAIN QUERY PLAN` 里能看到。

**洞察**：检查单"索引设计要跑 `EXPLAIN QUERY PLAN`"——底层就是：索引让查询从 O(n) 全表扫描变成 O(log n) 树查找。B+ Tree 和内存层级一起解释了"索引为什么快"。

### 缓存局部性：刚读过的数据大概率还要读

**两条规律**：
- **时间局部性**：刚访问过的数据，短时间内很可能再访问（循环变量、热数据）
- **空间局部性**：访问了第 N 个，第 N+1 个很可能也要（数组顺序遍历）

**洞察**：CPU 缓存、Redis、lru_cache 全都靠这两条规律。缓存之所以有效，不是玄学——是程序的访问模式天生具有局部性。检查单"哪些结果可缓存"的底层判断标准：这个数据有局部性吗？

### 池化思想：连接池/线程池为什么快

**核心问题**：创建连接很贵（TCP 握手 + 认证 + 建立会话），每次都新建 = 重复付固定成本。

**池的本质**：把固定成本**摊销**。一次性建好一批连接放在池里，请求来的时候拿现成的，用完归还。省掉的不是"连接时间"而是"反复的建造成本"。

**池要处理的三个决策**：
1. 池空时等还是新建？（QueuePool 默认等待）
2. 拿到的连接还活着吗？（`pre_ping` 发 `SELECT 1` 验证）
3. 池上限后怎么办？（`max_overflow` 临时扩容）

### 垃圾回收：内存什么时候释放、泄漏长什么样

**核心问题**：Python 对象用完不手动释放，谁负责回收？什么时候回收？

**CPython 的机制**：引用计数为主——对象引用数归零立即回收；循环引用靠分代 GC 周期扫描。GC 不是瞬时的，大对象的回收有延迟。

**泄漏的本质**：不是"忘了释放"，而是**引用还在**——对象被某个存活对象引用着，永远不归零。典型：全局缓存只增不减、闭包持有大对象、监听器注册了不注销。

**洞察**：检查单"跑 1000 个操作后内存是否持续增长"——测的就是泄漏。内存曲线不回头 = 有对象被永久引用 = 泄漏。

## 工程实践手段

| 原理 | 落地动作 |
|------|---------|
| 大 O | 瓶颈算法先估复杂度；`if x in list` → `if x in set`（O(n)→O(1)） |
| 内存层级 | 索引减少磁盘读；热点数据缓存到内存 |
| B+ Tree | `EXPLAIN QUERY PLAN` 看是否全表扫描；`CREATE INDEX`；避免 `SELECT *` |
| 局部性 | 缓存设 TTL/LRU + 上限（三者至少一个，不设上限 = 内存泄漏） |
| 池化 | SQLAlchemy Pool + `pre_ping`；`pool_size` + `max_overflow` |
| 垃圾回收 | 长时间运行测试监控内存曲线；缓存/监听器设清理路径 |
| 分页 | keyset/cursor（`WHERE id > last LIMIT N`）替代 OFFSET |
| 分析 | py-spy（采样，可上生产）/ scalene（内存逐行）/ cProfile（精确） |

## 推荐开源项目（跨语言）

| 项目 | 语言 | 定位 | 优势 | 劣势 / 风险 | 适用场景 |
|------|------|------|------|------------|---------|
| **py-spy** | Rust | 采样剖析 | 零侵入、可 attach 运行中进程、生产安全 | 采样不精确，短函数看不到 | Python 生产热点定位 |
| **cProfile** | Python | 插桩剖析 | 标准库、精确、零依赖 | 开销 10-30%、需重启 | 开发环境精确测量 |
| **scalene** | Python | CPU+内存剖析 | 逐行内存分配、同时看泄漏 | 较新、生态小 | Python 内存问题定位 |
| **perf** | Linux | 系统级剖析 | 硬件计数器、火焰图、内核级 | 学习曲线陡、Linux only | 深层次系统调优 |
| **k6** | Go | 负载测试 | 脚本化、云原生、结果可 CI | 重 JS 脚本 | API/接口压测 |
| **Apache JMeter** | Java | 负载测试 | 老牌、GUI、复杂场景 | 重、内存占用大 | 复杂压测场景 |
| **EXPLAIN QUERY PLAN** | SQL | SQL 分析 | 内置、零依赖 | 只针对单条 SQL | 每条慢查询都该跑 |
| **gperftools** | C++ | 剖析 | 多语言、堆剖析 | 需编译接入 | C/C++ 项目 |

**选型建议**：Python 从 py-spy（热点）+ scalene（内存）开始，这俩都能在生产环境安全用。压测用 k6，结果进 CI。SQL 慢一律先 `EXPLAIN`。
