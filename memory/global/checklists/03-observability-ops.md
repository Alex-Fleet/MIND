# 可观测性与运维检查单

> 核心问题：出问题了你多久能发现？发现了多久能恢复？
> 三根柱子：日志（离散事件）、指标（聚合数值）、追踪（全链路）
>
> 优先级说明：🔴 不做会丢数据/系统崩溃 | 🟡 不做有隐患 | 🟢 锦上添花

---

## 开工前（设计阶段）

- [ ] 🔴 **关键路径埋点**：每个关键操作是否可追踪？开始/结束/耗时/结果？**不做的代价：出问题只能靠猜，排障时间 ×10。**
- [ ] 🔴 **结构化日志**：统一 `key=value` 格式。`operation=ingest project=xxx duration=1.2s status=ok` > "ingest完成"
- [ ] 🔴 **日志级别规范**：DEBUG（调试）/ INFO（关键状态）/ WARNING（可恢复异常）/ ERROR（需人工）
- [ ] 🔴 **敏感信息过滤**：日志不会意外记录密钥/密码/用户隐私吗？
- [ ] 🔴 **日志轮转**：按大小/按时间切割，保留最近 N 个，不无限膨胀
- [ ] 🔴 **健康检查**：能否一个命令确认"系统在正常跑"？（HTTP /health / 心跳文件 / 端口检测）**不做的代价：系统崩了几天才发现。**
- [ ] 🟡 **SLI/SLO/SLA 定义**：SLI（测量什么，如 P99 延迟）→ SLO（目标是多少，如 P99 < 500ms）→ SLA（达不到的后果，如退款）。**不做的代价：不知道"够不够好"，优化没有方向，用户投诉没有标准。**
- [ ] 🟡 **告警设计**：什么情况告警？谁来响应？告警抑制做了吗（同一个问题不要发 100 条）？**不做的代价：告警风暴 → 疲劳 → 忽略 → 真正的问题被淹没。**
- [ ] 🟡 **RunBook 准备**：每条告警对应一个修复步骤文档。半夜被叫醒的人能照着操作，不需要现场思考。**不做的代价：出问题时只有写代码的人能修，而他在睡觉。**
- [ ] 🟡 **安装流程标准化**：全新环境从头开始，每一步有明确命令，有安装脚本
- [ ] 🟡 **启停标准化**：启动脚本 + 优雅停止（SIGTERM） + 强制停止（SIGKILL）
- [ ] 🟡 **配置管理**：安装时配一次的 vs 运行时经常调的，分开管理；变更进 git（除密钥）

## SLI/SLO/SLA 快速定义法

```
SLI（指标）    → 你到底在测量什么？    例：API 请求成功率
SLO（目标）    → 多好算够好？           例：成功率 ≥ 99.9%（月度）
SLA（后果）    → 达不到会怎样？         例：低于 99.0% 退款的 10%

先从一个 SLI 开始，不用贪多。最常见起步三件套：
1. 可用性：成功请求 / 总请求
2. 延迟：P99 响应时间
3. 吞吐：每秒请求数
```

## 最小可行监控（优先级从高到低）

1. 🔴 **心跳** — 系统在跑吗？
2. 🔴 **错误计数** — 最近 1 小时多少 ERROR？
3. 🟡 **关键操作计数** — 今天几个摘要？几个 turn 摄入？
4. 🟡 **关键操作耗时** — 最慢的 ingest 用时？平均呢？
5. 🟡 **资源用量** — DB 多大？磁盘剩余？
6. 🟢 **P99 延迟** — 最慢 1% 的请求耗时多少？

## 上线前（验证阶段）

- [ ] 🔴 **全新安装测试**：删光数据从零装，每步走通，文档跟上
- [ ] 🔴 **回滚测试**：升级出问题能一键回到旧版吗？数据丢吗？
- [ ] 🔴 **重启恢复测试**：运行中 kill 进程再重启 → 数据完整？能继续？
- [ ] 🟡 **告警演练**：触发一条告警 → 能在 5 分钟内定位到对应 RunBook 吗？
- [ ] 🟡 **升级测试**：老版→新版，DB 迁移自动完成，配置兼容
- [ ] 🟡 **依赖就绪检查**：DB/API/端口不可用时启动 → 优雅报错还是崩？
- [ ] 🟡 **P99 延迟可知**：最慢 1% 的请求耗时多少？用户能接受吗？

## 常见翻车

| 翻车现场 | 原因 | 怎么防 | 级别 |
|---------|------|--------|------|
| 系统崩了几天才发现 | 无健康检查、错误日志无人看 | 健康检查 + 异常告警 | 🔴 |
| 排障只有 "something went wrong" | 日志无上下文 | 结构化日志：时间/操作/输入/结果/耗时 | 🔴 |
| 半夜告警没人会修 | 无 RunBook，知识在人脑里 | 每条告警→对应 RunBook 步骤 | 🔴 |
| 日志占满磁盘 | 无轮转 | log rotation：按大小切割，保留最近 N 个 | 🔴 |
| 同一问题发了 100 条告警 | 无告警抑制/去重 | 相同告警聚合，N 分钟内只发一次 | 🟡 |
| 指标全绿但业务坏了 | 只监控技术指标 | 业务指标：摘要成功率、注入成功率 | 🟡 |
| 不知道服务是不是"够快" | 没有定义 SLO | 定义 P99 延迟目标，月度统计达成率 | 🟡 |
| "只能在我机器上跑" | 安装依赖未声明、路径硬编码 | 全新环境从零装一遍，记录所有卡点 | 🟡 |
| 升级后不可用但回不去 | 没预演升级、没备份 | 部署前备份，有回滚命令 | 🟡 |
| 停止时数据丢失 | 直接 kill -9 | 捕获 SIGTERM，完成当前操作再退出 | 🟡 |

## 反例（来自 MIND）

- ✅ `install.py` 自动化安装 + `_is_dashboard_running()` 健康检查 — 好
- ✅ install.py 自动备份 settings.json — 回滚意识
- ✅ `operation_log` 表记录每次 inject/summarize — 数据在但无人看
- 🔴 无 log rotation — 日志无限增长
- 🔴 无正式 stop 脚本 — dashboard 靠手动杀
- 🟡 无 SLI/SLO 定义 — 不知道"正常"是什么
- 🟡 无告警机制 — 挂了等用户来报
- 🟡 无 RunBook — 出问题只有你知道怎么修
- 🟡 无升级迁移脚本 — 改 Schema 时怎么办？
- 🟡 无性能基线 — 不知道操作变慢了多少

## 底层原理：多久能发现、多久能恢复

### 百分位 vs 平均：为什么用 P99 不用平均值

**核心问题**：平均值被极端值欺骗。99 个请求 10ms + 1 个请求 10 秒，平均值 ≈ 110ms，看起来"挺快"。但那个用户等了 10 秒。

**P99 的含义**：把 100 个请求的延迟从小到大排，第 99 个的延迟。意思是"99% 的请求都比这个快"——也就是最慢 1% 的请求要等多久。

**为什么 P99 比平均重要**：平均值衡量"大多数人的运气"，P99 衡量"最倒霉的用户体验"。1% 的慢请求如果来自重试风暴，它可能是系统即将雪崩的信号。

**洞察**：检查单"P99 延迟可知"的底层逻辑——用百分位揭示平均值藏起来的问题。

### Little's Law：为什么响应慢会导致雪崩

**数学公式**：`L = λ × W`（队列长度 = 到达率 × 平均耗时）

**一句话**：系统里"在等"的任务数量 = 每秒新来的任务数 × 每个任务平均待多久。

**为什么致命**：某个下游变慢，W（平均耗时）上升 → 队列 L 线性增长 → 请求排队更久 → 客户端超时重试 → 到达率 λ 也上升 → L 平方级爆炸。

**洞察**：这就是背压（见 02）和限流的数学依据。控制 λ（限流）或控制 W（降级/快速失败），本质是在公式里按下一个因子，防止 L 失控。

### RED vs USE：两套指标视角

| 指标体系 | 视角 | 指标 | 回答的问题 |
|---------|------|------|-----------|
| **RED** | 请求视角 | Rate（每秒请求）/ Errors（错误数）/ Duration（延迟） | 用户用起来怎么样？ |
| **USE** | 资源视角 | Utilization（利用率）/ Saturation（饱和）/ Errors（错误） | 机器扛得住吗？ |

**洞察**：两套都要。RED 告诉你业务坏了（指标全绿但用户投诉），USE 告诉你机器要挂了（CPU 99% 但还没报错）。检查单"指标全绿但业务坏了"——就是只配了 USE 没配 RED。

### 错误预算：SLO 的数学逻辑

**核心认知**：100% 可用性在数学上不现实——任何系统都会出故障。与其假装不会挂，不如**定义"够好"**。

**错误预算（Error Budget）**：SLO 是 99.9%？那 0.1%（约 43 分钟/月）就是你的错误预算。这 43 分钟里出故障是"预算内"的，不算事故。

**妙处**：错误预算把"质量"变成了可交易的数量。预算还有剩 → 可以放心上冒险的功能；预算花光了 → 冻结发布，只做稳定。

**洞察**：检查单"不知道服务是不是够快"——底层就是没定义错误预算。没有 SLO，就无法判断"这次事故算不算严重"。

### 日志/指标/追踪：三根柱子的分工

| 柱子 | 回答 | 数据形态 | 典型问题 |
|------|------|---------|---------|
| 日志 Logs | 单个事件发生了什么 | 非结构化文本 | "这次 500 的堆栈是什么" |
| 指标 Metrics | 一段时间内的总量/分布 | 数值聚合 | "今天错误率多少？" |
| 追踪 Traces | 一次请求穿越所有组件的全链路 | 有向图 | "这个慢请求卡在哪个服务？" |

**洞察**：三根柱子互补。指标告诉你"变慢了"（RED），日志告诉你"哪一行报错"，追踪告诉你"慢在哪个组件"。只留一个，定位问题要靠猜。

## 工程实践手段

| 原理 | 落地动作 |
|------|---------|
| 百分位 | 埋点 P50/P95/P99 三档，不只记平均 |
| Little's Law | 限流控 λ（令牌桶）+ 快速失败控 W（熔断） |
| RED + USE | 同时配业务指标（RED）和资源指标（USE），缺一不可 |
| 错误预算 | 定义 1 个 SLI + SLO（先不用贪多），月度统计达成率 |
| 三根柱子 | 结构化日志（loguru/structlog）+ 指标（prometheus）+ 追踪（OpenTelemetry，必要时） |
| 告警 | 阈值 + 抑制去重 + 每条告警配 RunBook（半夜被叫醒的人照着做） |
| 日志轮转 | loguru rotation="500 MB"，保留最近 N 个 |
| 健康检查 | `/health` endpoint + 心跳文件 + 定时巡检，挂了立即感知 |

## 推荐开源项目（跨语言）

| 项目 | 语言 | 定位 | 优势 | 劣势 / 风险 | 适用场景 |
|------|------|------|------|------------|---------|
| **Prometheus** | Go | 指标采集+告警 | 事实标准、拉模型、PromQL 强大、生态大 | 存储单机有上限，扩需 Thanos | 指标 + 告警规则 |
| **Grafana** | Go/TS | 可视化 | 多数据源、告警 UI、看板市场 | 本身不采集 | 看板 + 告警展示 |
| **Loki** | Go | 日志聚合 | 轻量、标签索引、与 Grafana 集成 | 全文查询能力弱于 ELK | 日志搜索 + 告警关联 |
| **OpenTelemetry** | 多语言 | 追踪标准 | 厂商中立、SDK 覆盖全语言 | 接入成本高、生态仍在磨合 | 分布式全链路追踪 |
| **Sentry** | Python/多 | 错误追踪 | 一行接入、自动分组、堆栈上下文 | 云端版付费、自托管要运维 | 未捕获异常监控 |
| **loguru** | Python | 结构化日志 | 零配置、自动上下文、轮转内置 | Python only | Python 日志起步 |
| **structlog** | Python | 结构化日志 | 数据与渲染分离、JSON 输出 | 概念要先理解 | Python 生产日志 |
| **zap** | Go | 高性能日志 | 极快、零分配 | Go only | Go 服务 |
| **supervisord** | Python | 进程守护 | 配置简单、自动重启 | 单机级 | 本地常驻进程 |
| **systemd** | C | 服务管理 | 系统原生、优雅停止完整 | Linux only | Linux 生产服务 |

**选型建议**：个人/小项目从 loguru + 定时巡检开始，不急着上 Prometheus/Grafana。数据量大了再加 Prometheus + Loki + Grafana 三件套（都比 ELK 轻）。
