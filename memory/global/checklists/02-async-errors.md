# 异步与错误处理检查单

> 核心问题：什么时候等、什么时候不等？不等的事挂了谁知道？崩了怎么收场？
>
> 优先级说明：🔴 不做会丢数据/系统崩溃 | 🟡 不做有隐患 | 🟢 锦上添花

---

## 开工前（设计阶段）

- [ ] 🔴 **快慢分离**：快路径上有慢操作（LLM/网络/大文件IO）吗？能移到后台吗？**不做的代价：用户请求被慢操作卡住超时，雪崩。**
- [ ] 🔴 **同步必要性质疑**：每一步问"这个必须等结果才能继续吗？"
- [ ] 🔴 **超时分级**：关键操作长超时+重试，非关键短超时+降级。每个操作都设了超时吗？**不做的代价：一个外部调用 hang 住，整个系统等死。**
- [ ] 🔴 **异常分类**：致命（不重试）/ 瞬态（可重试）/ 数据（降级）/ 逻辑（报告）— 分开了吗？
- [ ] 🔴 **重试策略**：什么错误可重试？重试几次？间隔多久？指数退避？
- [ ] 🔴 **熔断设计**：连续失败 N 次后停止尝试，保护自己也保护对方。**不做的代价：对方已经挂了你还疯狂重试，既浪费资源又延迟恢复。**
- [ ] 🔴 **异步失败处理**：后台任务挂了谁知道？（日志/回调/状态表/定时巡检？）**绝不 stdout/stderr 丢 DEVNULL**。**不做的代价：后台任务默默挂了几个月，发现时数据已经缺了一大片。**
- [ ] 🔴 **Fail-Secure 原则**：依赖不可用时，默认行为是"拒绝"还是"放行"？**认证服务挂了必须拒绝访问，不能放行。** 每个外部依赖问：它挂了，我是开放还是关闭？
- [ ] 🟡 **优雅关闭（Graceful Shutdown）**：收到 SIGTERM 后是否：①停止接收新请求 ②等待进行中的操作完成 ③释放连接/文件句柄 ④退出？**不做的代价：kill 时正在写的数据损坏、连接泄漏。**
- [ ] 🟡 **死信队列（Dead Letter Queue）**：重试全部失败的消息去哪了？是丢弃还是进 DLQ 等人工处理？**不做的代价：重试耗尽后消息静默丢失，业务数据对不上。**
- [ ] 🟡 **降级路径**：每个非关键依赖挂了能继续吗？关键路径不依赖非关键路径

## 上线前（验证阶段）

- [ ] 🔴 **异步失败测试**：故意让后台任务失败 → 多久被发现？日志有记录吗？
- [ ] 🔴 **超时测试**：让 LLM 调用卡 60s → 系统表现如何？能恢复吗？
- [ ] 🔴 **熔断测试**：LLM 连续返回 500 → 熔断触发了吗？降级行为对吗？
- [ ] 🔴 **重试不放大破坏**：重试的写入操作不会产生重复数据吗（幂等）？
- [ ] 🟡 **优雅关闭测试**：发送 SIGTERM → 进行中的操作完成了再退出吗？数据完整吗？
- [ ] 🟡 **死信队列测试**：全部重试失败后 → 消息进了 DLQ 还是丢了？
- [ ] 🟡 **Fail-Secure 测试**：认证服务挂了 → 请求被拒绝（正确）还是被放行（错误）？
- [ ] 🟡 **异常注入测试**：断网、DB 权限变只读、磁盘满 → 每种情况的表现？
- [ ] 🟡 **日志不爆炸**：一个错误连续触发 1000 次，日志会占满磁盘吗？

## 错误分类速查

```
🔴 致命（Fatal）     → 立即中止，不重试。例：401/402/403，DB 文件丢失
🔴 瞬态（Transient） → 指数退避重试。例：超时、5xx、429、网络抖动
🟡 数据（Data）      → 静默降级，不崩管线。例：JSON 解析失败、字段缺失
🟡 逻辑（Logic）     → 报告但不中止。例：配置值非法、业务规则冲突
```

## 常见翻车

| 翻车现场 | 原因 | 怎么防 | 级别 |
|---------|------|--------|------|
| 后台任务挂了几周才发现 | stderr→DEVNULL | 异步输出必落盘，定时巡检 | 🔴 |
| kill 时数据损坏 | 无优雅关闭，直接 kill -9 | 捕获 SIGTERM，完成当前操作再退出 | 🔴 |
| `except: pass` 吞异常 | 图省事 | 绝不裸 except。至少 log，只对"明确知道不重要"的静默 | 🔴 |
| 认证服务挂了所有人能进 | fail-open 设计 | 外部依赖不可用时默认拒绝（fail-secure） | 🔴 |
| 重试无上限打爆 API | 没设熔断 | 指数退避 + 最大重试 + 熔断器 | 🔴 |
| 重试写入导致重复数据 | 没做幂等 | 所有写入用唯一约束 / 去重标记 | 🔴 |
| 重试耗尽消息丢失 | 无死信队列 | 最终失败的消息进 DLQ，保留现场等人工处理 | 🟡 |
| 异常日志无上下文 | 只记了 `print(e)` | 日志含：时间/操作/输入摘要/异常类型/traceback | 🟡 |
| 非关键路径挂了拖死关键 | 依赖方向混乱 | 关键路径不依赖非关键路径 | 🟡 |

## 底层原理：等与不等、挂了怎么办

### 事件循环：单线程怎么服务海量 IO

**核心问题**：同步代码里，一个网络请求的等待时间 = CPU 完全空闲。100 个请求排队，第一个等 1 秒，后面 99 个一起等。

**核心思路**：事件循环是一个永不停歇的调度器——检查哪些任务"就绪了"（数据到了、定时器到了），执行一小段，又回去等。等待时 CPU 不闲着，继续服务别的任务。

**类比**：同步服务员站在一桌客人旁边等他们看完菜单，其他桌全晾着。异步服务员同时照顾十桌——哪桌举手去哪桌。

**协程 vs 线程**：线程切换由操作系统决定（抢占式，有内核开销），协程切换靠主动 `await`（协作式，几乎零成本）。**关键陷阱**：async 函数里如果没有 `await`，它就是同步的，会阻塞整个事件循环。

### 状态机：重试、熔断、限流的共同本质

**核心洞察**：重试/熔断/限流看着是不同工具，本质都是**有限状态机**——事件驱动状态转移。

```
熔断器： 关闭(统计失败) →失败达阈值→ 打开(直接拒绝) →超时→ 半开(试几个) →成功→ 关闭
重试器： 等待(退避) →尝试→ 失败→ 等待(更长) → 达到上限→ 放弃
限流器： 满(拒绝) →时间流逝→ 有额度(放行)
```

**为什么想成状态机**：状态机强迫你想清楚——每个状态下的行为是什么、什么事件触发转移。这比写 `if 失败: 再试一次` 的散乱逻辑可靠得多。检查单里的"熔断三态（关闭→打开→半开）"就是最典型的状态机。

### 背压：生产者太快，消费者跟不上

**核心问题**：任务产生速度 > 处理速度。队列会无限增长，最终内存爆炸或任务全部超时。

**背压（Backpressure）三选一**：
1. **丢弃**：新任务直接拒绝（返回 429/503），保护已有任务
2. **限流**：限制生产者的速度（令牌桶）
3. **阻塞**：生产者停下来等消费者（同步队列）

**洞察**：不处理背压 = 雪崩。请求堆积 → 每个请求等待更久 → 触发重试 → 更多请求 → 系统更慢。Little's Law（见 03）解释了这个恶性循环的数学。

### 两将军问题：为什么 Exactly-Once 不可能

**核心问题**：两军隔着峡谷要约定进攻时间，只能靠信使渡河。信使可能被抓，需要确认信使到达，确认的确认又需要确认……无限递归，永远无法达成"确定知道对方知道了"。

**推论**：任何分布式系统中，消息传递的"恰好一次"（Exactly-Once）在理论上不可能完美实现。你只能在**至少一次**（At-Least-Once，可能重复）和**至多一次**（At-Most-Once，可能丢失）之间选择。

**工程含义**：选择 At-Least-Once 时，处理函数必须**幂等**（见 01）——重复执行结果一样。这就是为什么任务队列和幂等总是一起出现。

### 错误分类学：哪些错误值得重试

**核心问题**：不是所有错误都应该重试。重试一个 401（密钥错了）只会重复失败，还浪费资源。

| 类别 | 是否重试 | 例 |
|------|---------|-----|
| 致命 Fatal | 永不重试，立即中止 | 401/403、DB 文件丢失 |
| 瞬态 Transient | 指数退避重试 | 超时、5xx、429、网络抖动 |
| 数据 Data | 不重试，降级跳过 | JSON 解析失败、字段缺失 |
| 逻辑 Logic | 不重试，报告 | 配置非法、业务规则冲突 |

**洞察**：分类是重试策略的前置步骤。不分类就重试 = 该认输的还在死磕，浪费资源；该重试的反而放弃，丢失数据。

## 工程实践手段

| 原理 | 落地动作 |
|------|---------|
| 事件循环 | asyncio + `asyncio.wait_for` 设超时；CPU 密集用 `run_in_executor` |
| 重试状态机 | tenacity：指数退避 + jitter + `retry_if_exception` 谓词 |
| 熔断状态机 | pybreaker：失败阈值 + 恢复超时 + 半开探测数 |
| 背压 | 队列上限 + 满则拒绝（429）；限流用令牌桶 |
| At-Least-Once | 任务队列（RQ/arq）+ 处理函数幂等 + 死信队列兜底 |
| 错误分类 | 异常分类表 + `call_llm()` 只对 Transient 重试 |
| 失败可见 | 后台任务日志落盘 + 状态表 + 定时巡检，**绝不 DEVNULL** |
| 优雅关闭 | 捕获 SIGTERM → 停止接收 → 完成在途 → 释放连接 → 退出 |

## 推荐开源项目（跨语言）

| 项目 | 语言 | 定位 | 优势 | 劣势 / 风险 | 适用场景 |
|------|------|------|------|------------|---------|
| **tenacity** | Python | 重试 | 指数退避+jitter+谓词、API 直观 | 仅重试，无熔断 | Python 外部调用 |
| **resilience4j** | Java | 重试+熔断+限流+舱壁 | 功能全、线程安全、配置驱动 | 学习曲线陡、概念多 | JVM 微服务 |
| **Polly** | .NET | 弹性策略 | 策略可组合、声明式 | 绑定 .NET | C# 服务 |
| **pybreaker** | Python | 熔断 | 三态状态机、轻量 | 功能单一 | Python 下游熔断 |
| **backoff** | Python | 重试 | 极简、装饰器即用 | 功能少 | 一次性脚本 |
| **Redis** | C | 队列/限流后端 | 原子操作、`BRPOPLPUSH` 可靠消费 | 内存、无持久 | 轻量任务队列 |
| **RabbitMQ** | Erlang | 消息队列 | AMQP 标准、路由灵活、管理 UI、ack 完整 | 运维重、需独立部署 | 复杂路由/多消费者 |
| **Apache Kafka** | Scala/Java | 事件流平台 | 高吞吐、持久化、可重放、at-least-once | 很重、运维复杂、学习成本高 | 日志流/事件溯源 |
| **RQ / arq / Celery** | Python | 任务队列 | RQ 简单、arq async、Celery 企业级 | 规模越大配置越复杂 | 按规模选，见下方对比 |

**任务队列三选一**：
| | RQ | arq | Celery |
|---|-----|-----|--------|
| 简单度 | ★★★★★ 直接 enqueue 函数 | ★★★★ async 原生 | ★★ 配置多 |
| 可靠性 | at-most-once | at-least-once | at-least-once |
| 适合 | 脚本级后台任务 | asyncio 项目 | 多队列/定时/分布式 |

**选型建议**：先重试（tenacity）+ 熔断（pybreaker）打底，任务队列从 RQ 起步。吞吐过万才考虑 Kafka。
