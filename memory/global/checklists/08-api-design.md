# API 设计检查单

> 核心问题：别人（包括三个月后的你）调用你的接口，会不会骂娘？
>
> 优先级说明：🔴 不做会丢数据/系统崩溃 | 🟡 不做有隐患 | 🟢 锦上添花

---

## 开工前（设计阶段）

- [ ] 🔴 **命名一致性**：动词+名词统一？`get_xxx` / `list_xxx` / `create_xxx` / `delete_xxx` / `ensure_xxx`？
- [ ] 🔴 **参数设计**：必填在前、可选在后。默认值合理。flag 用 enum 不用 bool
- [ ] 🔴 **返回值一致性**：成功时返回什么？失败时？同类型函数格式一致？
- [ ] 🔴 **错误信息可用性**：调用方看到错误能定位问题吗？还是只写 "Error occurred"？
- [ ] 🔴 **向后兼容**：改接口会破坏现有调用方吗？加新参数，旧参数保留过渡期
- [ ] 🔴 **幂等性设计**：支付/扣款/写入类接口是否支持幂等 key？同一请求发两次结果一致吗？**不做的代价：网络超时用户重试→扣了两次钱/写了两条数据。**
- [ ] 🟡 **版本策略**：对外 API 有版本号吗（`/api/v1/`）？什么时候升版本？
- [ ] 🟡 **限流与配额**：有调用频率限制吗？超过返回什么（429）？用什么算法（令牌桶/滑动窗口/固定窗口）？**令牌桶允许短时突发，滑动窗口更平滑。不做的代价：一个 bug 循环就能打爆你的服务。**
- [ ] 🟡 **文档同步**：实现和文档同步更新吗？作为 PR 检查项？

## 命名一致性规范

```
get_xxx()       → 返回单个对象或 None，找不到返回 None
list_xxx()      → 返回列表，找不到返回空列表（不是 None！）
create_xxx()    → 创建并返回新对象
update_xxx()    → 更新并返回更新后的对象
delete_xxx()    → 删除，返回 bool 或 None
ensure_xxx()    → 存在就返回，不存在就创建（幂等）
```

同一个模块里 `get_turns()` 返回 None 但 `get_sessions()` 返回空列表 —— 不一致，调用方要写一堆 if。

## 限流策略速查

```
固定窗口   → 1分钟内最多 N 次。简单但边界有突刺（59秒和00秒各 N 次）
滑动窗口   → 过去 1 分钟内最多 N 次。平滑但实现稍复杂
令牌桶     → 桶里最多 N 个令牌，匀速补充。允许短时突发
漏桶       → 请求进队列，匀速处理。强制定速，不允突发

API 限流推荐：令牌桶（允许合理突发）+ 硬上限（绝对不超）
```

## 幂等性实现模式

```python
# 方式 1：客户端生成幂等 key
# POST /api/payment  Header: Idempotency-Key: abc-123
# 服务端：key 已存在 → 返回之前的结果，不重复执行

# 方式 2：数据库唯一约束兜底
# INSERT ... ON CONFLICT (idempotency_key) DO NOTHING
```

## 函数签名范例

```python
# ✅ 好的
def get_turn_summaries_in_window(days: int, project: str | None = None, limit: int = 150)

# ❌ 不好
def get_stuff(d, p=None, l=150)  # 参数名不表意

# ❌ 可怕
def process(flag, data=None, mode="fast", *args, **kwargs)  # 完全不知道干什么
```

## 上线前（验证阶段）

- [ ] 🔴 **幂等性测试**：同一请求发两次 → 结果一致吗？第二次没重复扣费/写入吗？
- [ ] 🔴 **异常输入测试**：错类型、超长串、负数 — API 返回什么？
- [ ] 🔴 **并发调用**：同样参数同时调两次 — 返回一致吗？副作用冲突吗？
- [ ] 🟡 **新手 5 分钟测试**：找个没用过的同事看文档，5 分钟内能调通吗？
- [ ] 🟡 **破坏性变更通知**：不兼容改动的调用方都通知到了？有迁移指南？
- [ ] 🟡 **废弃流程**：旧接口标记废弃后有日落时间？警告信息写了替代方案？
- [ ] 🟡 **限流测试**：超过限制 → 返回 429 了吗？Retry-After header 设了吗？

## 常见翻车

| 翻车现场 | 原因 | 怎么防 | 级别 |
|---------|------|--------|------|
| 改了参数名下游全炸 | 无向后兼容 | 加新参数，旧参数过渡期保留 | 🔴 |
| 网络超时重试扣两次款 | 无幂等 key | 幂等 key + 数据库唯一约束兜底 | 🔴 |
| 返回格式不统一 | 有的是 dict 有的是 list 有的抛异常 | 统一 `{ok, data, error}` | 🔴 |
| 一个死循环打爆 API | 无限流 | 每用户/每 IP 限流，令牌桶+硬上限 | 🟡 |
| 文档和实现不一致 | 改了代码没改文档 | 文档和代码一起 review | 🟡 |
| 外部 API 改了我们跟着炸 | 直接暴露第三方结构 | 抽象层隔离 | 🟡 |
| 参数类型过多 | `str | list[str] | None` 三种 | 拆分或明确文档说明 | 🟡 |

## 反例（来自 MIND）

- ✅ `store.py` 命名一致性：`get_xxx`, `insert_xxx`, `update_xxx` — 好
- ✅ 大部分函数参数有默认值 — 好
- 🟡 `get_turn_summaries_in_window` 的 `project` 参数：`str` / `list[str]` / `None` 三种 — 文档未说明
- 🟡 无 API 文档 — 调 `inject.py` 只能读源码
- 🟡 返回值类型不统一 — 功能不同可以理解但无统一错误处理模式
- 🟡 无限流机制 — 看板每 12s 轮询全量数据，毫无防护

## 底层原理：别人调用会不会骂娘

### 幂等的数学定义：f(f(x)) = f(x)

**核心问题**：调用方网络超时会重试。你的接口扛得住重试吗？

**数学定义**：对操作 f 和任意 x，`f(f(x)) = f(x)`——执行两次和执行一次结果相同。

**为什么网络接口必须幂等**：客户端发出请求 → 服务器执行了 → 但响应在网络上丢了 → 客户端以为失败，重试 → 服务器又执行一次。**如果操作不幂等，重试 = 重复副作用**（扣两次钱、插两条数据）。

**工程实现两条路**（二选一或都做）：
1. **幂等 key**：客户端每次操作带唯一 key，服务端记住 key，重复请求直接返回第一次的结果
2. **数据库约束兜底**：`INSERT ... ON CONFLICT DO NOTHING`——重复插入被 UNIQUE 吃掉

**洞察**：检查单"幂等性设计"的底层逻辑——这是重试的前提（见 02）。不幂等的接口 + 网络重试 = 必然出数据错误。

### 接口契约：调用方与提供方的隐式约定

**核心认知**：你的函数签名/接口格式不只是一段代码——它是一个**契约**（Contract）：提供方承诺"给定这些输入，我这样返回"，调用方依赖这个承诺。

**契约的组成部分**：
- **前置条件**：合法的输入范围（必须非负、必填参数）
- **后置条件**：返回的格式和语义（总是 dict？找不到返回 None？）
- **不变量**：调用前后系统状态不破坏

**洞察**：检查单"返回值一致性"的底层逻辑——不一致的返回 = 打破契约 = 调用方得为每种情况写分支。契约越清晰，调用方代码越简单。三个月后的你也是调用方。

### REST vs RPC vs GraphQL：三种范式的取舍

| | REST | RPC | GraphQL |
|---|------|-----|---------|
| 心智模型 | 资源 + 动词 | 远程函数调用 | 按需查询图 |
| 例 | `GET /users/42` | `getUser(42)` | `query { user(id:42) { name } }` |
| 适合 | 公开 API、资源模型清晰 | 内部服务间、动作多 | 客户端需求差异大、要少请求 |
| 代价 | 复杂查询要多请求 | 语义模糊、难缓存 | 服务端复杂度、缓存难 |

**洞察**：没有"最好"，只有"匹配"。MIND 的看板 API 是资源模型（feed/projects）→ REST 合适。检查单"动词+名词统一"就是 REST 资源语义的落地。

### 分布式计算的八个谬误：想当然的假设

**Peter Deutsch 整理的八个想当然**——新手分布式系统里最容易踩的假设：

1. 网络是可靠的
2. 网络延迟是零
3. 带宽是无限的
4. 网络是安全的
5. 拓扑结构不会变
6. 只有一个管理员
7. 传输成本是零
8. 网络是同构的

**全部是错的**。每个假设对应一类事故：假设 1 → 超时重试必须处理；假设 2 → 每步调用都设超时；假设 4 → 默认数据可被窃听，要加密。

**洞察**：检查单"外部调用设超时、重试、鉴权过期"——底层就是把这八个谬误当成默认假设来防御。**在分布式系统里，乐观 = 出 bug。**

### 向后兼容策略：改动不打破现有调用方

**核心问题**：接口要演进，但改坏了现有调用方怎么办？

**策略**：
1. **加而不删**：加新参数/新端点，不删旧的。旧调用方不受影响
2. **新参数给默认值**：缺省时行为等价旧版
3. **版本化**：不兼容改动放 `/api/v2/`，旧的 `/api/v1/` 继续跑 + 日落时间
4. **废弃流程**：标记 deprecated → 告警信息写替代方案 → 给过渡期 → 才删除

**洞察**：检查单"旧参数保留过渡期"——底层是信任。调用方按契约投资了你的接口，你单方面破坏契约 = 别人的系统无预警地坏掉。向后兼容是接口提供方的**职业道德**。

## 工程实践手段

| 原理 | 落地动作 |
|------|---------|
| 幂等 | 写接口带 `Idempotency-Key` header + UNIQUE 约束兜底 |
| 契约 | 统一返回格式 `{ok, data, error}`；`get` 找不到返回 None，`list` 找不到返回空列表 |
| 范式 | 资源模型用 REST；动作多用 RPC；按需查询用 GraphQL |
| 八个谬误 | 每个外部调用：超时 + 重试 + 熔断 + 鉴权过期处理 |
| 向后兼容 | 加参数不删参数；新参数默认值；破坏性变更升版本号 |
| 废弃 | deprecated 标记 + 替代提示 + 日落时间 |
| 限流 | 令牌桶（允许合理突发）+ 429 + `Retry-After` header |
| 文档 | OpenAPI 自动生成（代码即文档），PR 时文档同步 review |

## 推荐开源项目（跨语言）

| 项目 | 语言 | 定位 | 优势 | 劣势 / 风险 | 适用场景 |
|------|------|------|------|------------|---------|
| **FastAPI** | Python | HTTP 框架 | 异步、Pydantic 校验、OpenAPI 自动生成 | Python only | 新 Python API，**首选** |
| **Flask** | Python | HTTP 框架 | 简单、生态大、教程多 | 手动路由、无自动文档 | 小型/传统 |
| **Express** | Node | HTTP 框架 | 生态最大、上手快 | 手动拼中间件、无自动校验 | Node API |
| **NestJS** | Node/TS | HTTP 框架 | 结构化、依赖注入、TS | 学习曲线、重 | 大型 TS 项目 |
| **Spring Boot** | Java | 企业级框架 | 生态全、稳定、人才多 | 重、启动慢 | 大企业后端 |
| **Gin** | Go | HTTP 框架 | 高性能、中间件 | 生态相对小 | Go 高并发 |
| **OpenAPI Generator** | 多语言 | 客户端生成 | 一份规范出多语言 SDK | 规范先行，改接口要同步 | 多客户端场景 |
| **Kong** | Lua | API 网关 | 认证/限流/插件化 | 运维成本 | 多服务网关 |
| **Traefik** | Go | 反向代理+网关 | 配置即代码、自动发现 | 功能偏基础 | 容器化网关 |

**选型建议**：Python 直接 FastAPI（自动文档+校验零成本）；契约一致性用 OpenAPI 规范先行。限流网关层用 Kong/Traefik，应用层自己用令牌桶。
