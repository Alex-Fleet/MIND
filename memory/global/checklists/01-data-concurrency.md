# 数据持久化与并发检查单

> 核心问题：写进去的东西真的在了吗？两个操作同时发生会怎样？
>
> 优先级说明：🔴 不做会丢数据/系统崩溃 | 🟡 不做有隐患 | 🟢 锦上添花

---

## 开工前（设计阶段）

- [ ] 🔴 **WAL 模式**：SQLite 是否开了 `PRAGMA journal_mode=WAL`？WAL 下写不阻塞读，崩溃可恢复。**不做的代价：崩溃后 DB 文件损坏，数据全丢。**
- [ ] 🔴 **事务边界**：多步写操作是否包裹在事务里？失败是否整体回滚？部分成功是否留脏数据？**不做的代价：写一半崩了，数据处于逻辑矛盾状态，无法修复。**
- [ ] 🔴 **原子写入**：关键写入是否"要么全成功、要么全失败"？
- [ ] 🔴 **幂等设计**：同一操作执行两次，结果一致吗？UNIQUE 约束 / 去重标记 / 版本号？**不做的代价：重试操作产生重复数据，统计全乱。**
- [ ] 🟡 **Schema 变更策略**：加字段/改表结构有迁移脚本吗？每个 migration 有对应的 `down()` 回滚方法吗？老版本数据在新版能读吗？
- [ ] 🟡 **Migration 回滚设计**：每个 `up` migration 都有对应的 `down` 吗？回滚后数据能恢复到迁移前的状态吗？**不做的代价：升级出问题只能手动修数据，停服时间不可控。**
- [ ] 🟡 **锁策略**：乐观锁还是悲观锁？读多写少→乐观，写多→悲观。所有锁的获取顺序一致吗（防死锁）？
- [ ] 🟡 **竞态分析**：画一下两个请求同时进来的执行路径，交叉点在哪？
- [ ] 🟡 **连接管理**：DB 连接是共享还是每次新建？用完是否立刻归还/关闭？
- [ ] 🟢 **读写分离**：读多写少的场景是否考虑读副本？至少要知道这个选项存在。

## 上线前（验证阶段）

- [ ] 🔴 **备份恢复演练**：不仅要有备份。最近一次从备份恢复到新环境并成功启动是什么时候？**不做的代价：备份文件本身损坏而你不知道，真出事恢复不了。**
- [ ] 🔴 **写入后校验**：关键数据写入后立即读回验证
- [ ] 🔴 **并发写入测试**：两进程同时写同一行/同一文件 → 结果对吗？没有丢数据？
- [ ] 🔴 **崩溃恢复测试**：写入中途 kill 进程，重启后数据完整吗？
- [ ] 🟡 **Migration 回滚测试**：`up → down → up` 循环执行，数据完整吗？down 真的能回滚吗？
- [ ] 🟡 **读写并发测试**：一个在读、一个在写同一行 → 读到的是什么？
- [ ] 🟡 **定时任务重叠测试**：上次没跑完、新一次又触发 → 会崩还是跳？
- [ ] 🟡 **备份策略确认**：备份存哪？异地吗？多长时间备一次？保留几份？
- [ ] 🟡 **磁盘空间监控**：接近上限是否告警？
- [ ] 🟡 **大型写入测试**：一次写 10000 条，DB 锁多久？

## 常见翻车

| 翻车现场 | 原因 | 怎么防 | 级别 |
|---------|------|--------|------|
| DB 文件损坏无法恢复 | 没开 WAL / 没备份 | 开 WAL，定期备份并验证完整性 | 🔴 |
| 备份文件损坏恢复时才发现 | 只备份不验证，从不演练恢复 | 定期恢复演练：从备份→新环境→启动成功 | 🔴 |
| SQLite `database is locked` | 多进程同时写，没重试 | 设 `busy_timeout`，写操作加重试 | 🔴 |
| 写入成功但读到旧数据 | 事务隔离级别不对 / 没在同一事务 | 读+写放同一事务；关键读用一致性级别 | 🔴 |
| 崩溃后 DB 损坏 | 没开 WAL，写到一半崩了 | `PRAGMA journal_mode=WAL` | 🔴 |
| 升级失败回不去 | migration 没写 down() | 每个 migration 必须有 down，提交前测回滚 | 🟡 |
| 定时任务重叠导致重复处理 | 无运行状态锁 | 运行时写 lock/pid 文件，启动前检查 | 🟡 |
| 两个操作各自成功但逻辑矛盾 | 应原子但分开了 | 事务包裹两步操作 | 🟡 |
| 升级后老数据读不了 | Schema 变了没迁移脚本 | 版本化 Schema，迁移脚本随版本走 | 🟡 |

## 反例（来自 MIND）

- 🔴 `nailong.db` 211MB 无异地备份 — 硬盘坏全丢
- 🔴 ingest 写入无显式事务 — `UNIQUE` 约束只是兜底不是保护
- 🟡 Stop hook 和 SessionStart catchup 可能同时调 `summarize.py` → 双倍 LLM 花费
- 🟡 没有运行锁 — 定时 digest 重叠时行为未定义
- 🟡 无 migration 机制 — 改 Schema 靠手动 SQL，无法回滚

## 底层原理：这些检查在防什么

### 磁盘 vs 内存：数据"真的在"是什么

**核心问题**：内存断电即失。一个值存在内存里，机器一断电就没了。数据持久化的第一前提是落盘。

**关键认知**：写文件 ≠ 真的写进了磁盘。数据从程序 → 内核缓冲区 → 磁盘，中间隔了两层缓存。`fsync`/`flush` 才是"确保真的到磁盘"。操作系统可能在宕机时丢掉缓冲区里还没落盘的数据。

**洞察**：这就是为什么"写入后校验 + 崩溃恢复测试"是检查单的 🔴 项——你不仅要写，还要确认它穿越了所有缓存层真正落盘了。

### WAL（Write-Ahead Log，预写日志）

**核心思路**：不直接改数据文件。任何修改先追加到日志文件（顺序写），日志落盘了再回头更新数据文件（随机写）。

**为什么快？** 磁盘顺序写的速度是随机写的 10~100 倍。WAL 把所有昂贵的随机写，变成了"先顺序写日志（快），后台再慢慢消化（可异步）"。

**为什么安全？** 崩溃了怎么办？重启时重放日志——日志里记的修改重做一遍。数据文件里写了一半的页，被日志内容覆盖。这就是 ACID 里 **D（持久性）** 的保障。

**MIND 关联**：`PRAGMA journal_mode=WAL` 之后，ingest 写入和看板读取可以同时进行（写不阻塞读）。不开 WAL？写的时候读被阻塞，看板就卡住。

### ACID：事务的四个承诺

| 字母 | 含义 | 一句话 | 对应检查单条目 |
|------|------|--------|---------------|
| **A** 原子性 | 要么全做，要么全不做 | 转账扣了你的钱但没加到对方 → 原子性失败 | "事务包裹多步写入" |
| **C** 一致性 | 数据库永远满足约束 | UNIQUE、FOREIGN KEY、CHECK 不被违反 | "写入后校验" |
| **I** 隔离性 | 并发事务互不干扰 | 两个操作同时改同一行，结果还对 | "竞态分析""读写并发测试" |
| **D** 持久性 | 提交的东西不会丢 | 崩溃重启后数据还在 | "崩溃恢复测试"、WAL |

**洞察**：整个数据并发检查单就是 ACID 的操作化。每条检查都在捍卫这四个承诺之一。WAL 是实现 D 的手段，事务是实现 A 的手段。

### 事务隔离级别：并发事务互相干扰到什么程度

**核心问题**：两个事务同时跑，允许它们看到彼此的中间状态吗？四个级别从松到严：

| 级别 | 防住的 | 没防住的 |
|------|--------|---------|
| Read Uncommitted | 什么都防不住 | 脏读（读到别人没提交的数据） |
| Read Committed | 脏读 | 不可重复读（同查询两次结果不同） |
| Repeatable Read | 脏读 + 不可重复读 | 幻读（范围查询时别的行被插入） |
| Serializable | 全部 | 无 |

**洞察**：SQLite 默认是 Serializable（全串行），最安全但并发写受限。检查单说"读+写放同一事务、关键读用一致性级别"——底层就是选择隔离级别：你要牺牲多少并发来换多少一致性。

### MVCC（Multi-Version Concurrency Control）

**解决的问题**：读写并发。一个在写、一个在读，读的应该看到什么？

**核心思路**：写入不覆盖旧数据，而是创建新版本。每个事务开始时拍一张快照，只看到"我当时该看到的版本"。写提交后，后来的事务才看到新版本。

**好处**：读永不阻塞写，写永不阻塞读。这就是为什么 SQLite WAL + 事务可以同时读写。

**洞察**：检查单"读写并发测试"问的就是 MVCC 是否正常工作——读的事务是不是看到了该看到的版本，而不是读到写了一半的数据。

### 乐观锁 vs 悲观锁

| | 乐观锁 | 悲观锁 |
|---|--------|--------|
| 思路 | 假设冲突很少，提交时检查 | 假设冲突很多，操作前先锁 |
| 实现 | 版本号 / `WHERE version = ?` | `SELECT ... FOR UPDATE` / 文件锁 |
| 适用 | 读多写少，冲突罕见 | 写多，冲突频繁 |
| 失败代价 | 提交失败重试 | 阻塞、死锁风险 |

**洞察**：MIND 的 ingest 是"写多"场景——多进程同时写，乐观锁会导致大量重试。所以 SQLite 用 WAL + 写锁更合适。选哪个取决于冲突概率，不是偏好。

### 幂等性：重试安全的数学本质

**核心问题**：同一操作执行两次，结果必须和执行一次一样。

**数学定义**：f(f(x)) = f(x)。幂等操作的本质是"重复应用不改变结果"。

**为什么这重要**：网络是不可靠的——请求可能发出去了但响应丢了，客户端只能重试。如果操作不幂等，重试 = 重复执行 = 数据错误（转账扣两次、插入两条）。幂等性是"允许重试"的前提。

**工程实现**：
- 数据库层面：UNIQUE 约束 + UPSERT（`INSERT ... ON CONFLICT DO NOTHING`）
- 业务层面：请求带幂等 key，服务端记住 key，重复请求直接返回第一次的结果

**洞察**：检查单"重试的写入操作不会产生重复数据吗"——底层问的就是"这个操作幂等吗"。

### 乐观锁 vs 悲观锁

| | 乐观锁 | 悲观锁 |
|---|--------|--------|
| 思路 | 假设冲突很少，提交时检查 | 假设冲突很多，操作前先锁 |
| 实现 | 版本号 / `WHERE version = ?` | `SELECT ... FOR UPDATE` / 文件锁 |
| 适用 | 读多写少，冲突罕见 | 写多，冲突频繁 |
| 失败代价 | 提交失败重试 | 阻塞、死锁风险 |

**洞察**：MIND 的 ingest 是"写多"场景——多进程同时写，乐观锁会导致大量重试。所以 SQLite 用 WAL + 写锁更合适。选哪个取决于冲突概率，不是偏好。

## 工程实践手段

| 原理 | 落地动作 |
|------|---------|
| WAL | `PRAGMA journal_mode=WAL` + `busy_timeout=5000` + 定期 checkpoint |
| 事务 | 多步写显式 `BEGIN`/`COMMIT`，异常 `ROLLBACK`，失败整体回滚 |
| 隔离级别 | 明确声明，不依赖默认；读写放同一事务 |
| 幂等 | UNIQUE 约束 + UPSERT，重试安全不靠去重标记 |
| 持久性 | 关键写入后 `fsync` + 读回校验 |
| 备份 | `VACUUM INTO` 冷备（或 `sqlite3 .backup`）+ **定期恢复演练**，备份存异地 |
| 迁移 | Alembic up/down，提交前测 `downgrade` |
| 并发写 | 运行锁（pid 文件）+ 重试，多进程写串行化 |

## 推荐开源项目（跨语言）

| 项目 | 语言 | 定位 | 优势 | 劣势 / 风险 | 适用场景 |
|------|------|------|------|------------|---------|
| **SQLite** | C | 嵌入式关系库 | 零运维、单文件、WAL+MVCC 桌面级并发、部署量最大 | 单写者、无网络访问 | 单机/移动/嵌入式，**正确默认** |
| **PostgreSQL** | C | 服务器级关系库 | MVCC 最强、功能最全、生态大、扩展多 | 运维重、内存占用高 | 多用户/跨机器/高并发写 |
| **MySQL/MariaDB** | C/C++ | 服务器级关系库 | 生态大、教程多、云厂商原生 | 严格模式踩坑、默认行为需调 | 已选型团队的惯性场景 |
| **Redis** | C | 内存存储/缓存/队列 | 极快、数据结构丰富、原子操作、单线程无锁 | 内存贵、持久化弱、`KEYS *` 危险 | 缓存/会话/限流/轻量队列 |
| **Alembic** | Python | 数据库迁移 | 与 SQLAlchemy 集成、autogenerate | 绑定 SQLAlchemy | Python + SQLAlchemy |
| **Flyway** | Java | 数据库迁移 | 语言无关、纯 SQL、命令行 | JVM 生态依赖 | 非 Python 项目迁移 |
| **Barman** | Python | PG 备份/恢复 | 自动备份+恢复演练、配置简单 | 只支持 PostgreSQL | PG 生产备份 |

**选型建议**：单机先 SQLite（WAL 开满），要跨机器/高并发写才上 PostgreSQL。Redis 缓存要配淘汰策略，不当主存储。
