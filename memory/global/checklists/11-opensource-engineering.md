# 开源工程工具深度解析

> 10-reuse.md 告诉了你"用什么"。本文告诉"为什么这么设计"——让你遇到场景时不只是选工具，而是理解背后的思路，可以自己判断、可以借鉴到自己系统里。
>
> 不写代码，只讲思路。每个工具控制在 400 字以内。

## 一、重试：tenacity

**解决的问题**：网络抖一下、API 临时 503——这种瞬时故障不该让整个操作失败。

**核心机制——指数退避 + 随机 Jitter：**

每次重试的等待时间 = `base × 2^attempt`，再加上随机抖动。比如 base=1s：第 1 次等 1s，第 2 次等 2s，第 3 次等 4s...上限通常设 60s。

**为什么必须有 Jitter？** 假设 100 个客户端同时超时。没有 jitter = 所有客户端在同一时刻重试 = 瞬间把服务器打挂（雷鸣羊群效应）。加 jitter 让重试分散在时间窗口里，服务器有喘息空间。

**重试条件谓词**：不是所有错误都值得重试。tenacity 的 `retry` 参数让你精确控制——只重试 `HTTPError` 且 status_code ≥ 500，429 看 Retry-After header。401/403 绝对不重试。

**设计洞察**：重试不是"再试一次"那么简单。三条铁律——①退避递增（给恢复时间）②随机打散（防羊群）③条件过滤（该认输就认输）。

**何时用**：任何调用外部服务的地方。**何时不用**：本地操作（文件读写有自己的重试语义）、幂等性不保证的写入（除非你实现了幂等）。

## 二、熔断：pybreaker / circuitbreaker

**解决的问题**：下游已经挂了，你还一直调它——浪费自己资源，延迟恢复。

**核心机制——三态状态机：**

```
关闭(CLOSED) → 正常运行，统计失败次数
    ↓ 失败次数达阈值
打开(OPEN)   → 立即拒绝请求，不尝试。设一个超时
    ↓ 超时到期
半开(HALF_OPEN) → 允许少量探测请求通过
    ↓ 探测成功 → 关闭   探测失败 → 重新打开
```

**关键参数**：失败阈值（几次失败触发断开）、恢复超时（断开多久后尝试半开）、半开探测数（几条请求来判断"恢复了没"）。

**为什么不是简单的"连不上就跳过"？** 因为熔断器保护的是你自己。如果每次调下游都等 30s 超时，你的线程/连接很快耗尽。熔断后立即失败，不占资源。

**设计洞察**：熔断器本质是"快速失败"——与其等一个肯定不来的响应，不如立刻认输。这在大规模分布式系统里是生存技能。

**何时用**：任何跨网络调用。**何时不用**：本地调用、单机系统里没有网络边界的组件之间。

## 三、限流：令牌桶 vs 滑动窗口

**解决的问题**：一个 bug 循环就能打爆你的服务。限流是最后一道防线。

**令牌桶 (Token Bucket)：**

想象一个桶，系统每秒往里放 N 个令牌，桶最多装 B 个。请求来了需要拿一个令牌才能通过。令牌不够就拒绝。

核心洞察：桶的容量 B 决定了"允许的突发量"。假设速率 10/秒，桶容量 30——正常匀速 10/秒，但短时间可以爆发到 30/秒（只要桶里有存货），之后被速率限制拉回来。

这就是为什么令牌桶比固定窗口好：它允许合理突发（用户快速翻页），但不允许持续超速。

**滑动窗口 (Sliding Window)：**

不是按整点分窗口（固定窗口的致命缺陷：59 秒 100 次 + 00 秒 100 次 = 2 秒内 200 次），而是"过去 N 秒内最多 M 次"。实现通常用 Redis 的 Sorted Set：每次请求插入时间戳，统计过去 N 秒内的个数，删掉过期的。

**令牌桶 vs 滑动窗口对比**：令牌桶允许突发但长期匀速；滑动窗口严格限制任意 N 秒内的总量。API 限流推荐令牌桶——用户快速点 5 下按钮不应该被限。

**设计洞察**：限流不是简单的"1 分钟 100 次"。你得想清楚——允许突发吗？突发多大？超限是拒绝还是排队？

## 四、任务队列：RQ vs Celery vs arq

**解决的问题**：把慢操作（发邮件、生成报表、调 LLM）从用户请求路径上移走。

**核心模式——生产者-消费者：**

```
Producer → Broker(Redis) → Worker(消费任务)
                             ↓
                        Result Backend(Redis/DB)
```

生产者扔任务到队列，立刻返回。Worker 从队列取任务、执行、存结果。

**传递保证（Delivery Guarantee）——这是任务队列最难的部分：**

- **At-most-once**（RQ 默认）：任务可能丢，但绝不重复。适合非关键操作。
- **At-least-once**（Celery 默认）：任务绝不丢，但可能重复执行。适合关键操作，**但要求你的任务处理函数是幂等的**。
- **Exactly-once**：不存在。分布式系统里不可能完美保证。

**RQ 简单在哪？** 它直接序列化 Python 函数调用——`queue.enqueue(my_func, arg1, arg2)`。不需要注册 task、不需要定义消息格式。代价是 Worker 必须能访问相同的代码。

**Celery 重量在哪？** 独立的 task 注册、多传输协议（Redis/RabbitMQ）、复杂的路由、定时调度（Celery Beat）、结果存储、监控面板。适合多服务、多队列的企业级场景。

**arq 的不同思路**：async-first，基于 Redis 的 LIST + BRPOPLPUSH 做可靠消费。不序列化函数——你用 JSON 定义任务格式。轻量且支持 at-least-once。

**设计洞察**：选任务队列的核心问题是"允许丢任务吗？"。不允许丢→at-least-once→必须幂等。允许丢→at-most-once→更简单。

**何时用**：消耗 > 100ms 的非用户阻塞操作。**何时不用**：简单脚本不需要，直接 subprocess 跑。

## 五、结构化日志：loguru vs structlog

**解决的问题**：`print()` 能告诉你发生了什么，但不能帮你定位问题。结构化日志让你能搜索、聚合、关联。

**loguru 的核心理念——零配置 + 彩色 + 内置轮转：**

`logger.add("file.log", rotation="500 MB")` 一行搞定文件输出+轮转。比标准库 `logging` 少 90% 的样板代码。

背后做了什么：自动绑定线程 ID、进程 ID、时间戳（高精度）、调用位置。这些上下文信息不用你手动加——自动就有了。

**structlog 的核心理念——渲染分离：**

这是更深刻的洞察。structlog 把"产生日志数据"和"渲染日志输出"分成两步。第一步产生 dict：`{"event": "user_login", "user_id": 42, "ip": "1.2.3.4"}`。第二步自由渲染：开发环境彩色 console、生产环境 JSON 输出给 Loki/ELK。

为什么这很重要？因为日志的消费者不总是人。机器读 JSON，人读彩色文本。分离了数据和渲染，就可以在不动日志代码的前提下切换输出格式。

**loguru vs structlog 选择**：loguru 适合"我要一个更好的 print"；structlog 适合"我的日志要被机器消费"。

**设计洞察**：好的日志系统不靠 discipline 来让开发者手动加上下文——而是自动绑定上下文（线程/请求/用户），让每条日志都可追踪。

## 六、配置管理：pydantic-settings

**解决的问题**：配置散落在 `os.environ.get()` 各处，没有校验，没有默认值，没有文档。

**核心机制——优先级链：**

```
CLI 参数 > 环境变量 > .env 文件 > 代码默认值
```

每一层覆盖下一层。环境变量是运维级的，代码默认值是开发级的。pydantic-settings 用一个 BaseSettings 类声明所有的配置字段和类型，初始化时自动按优先级链解析。

**为什么类型校验很重要？** `DATABASE_TIMEOUT=abc` 应该启动时就报错，而不是运行到一半崩溃。Pydantic 在启动时完成所有校验，失败即停。

**设计洞察**：配置不是简单地"读环境变量"。配置管理有三层需求——①声明（有哪些配置）②校验（类型对不对、值合不合理）③文档（每个配置干什么）。pydantic-settings 三层都做了。

**何时用**：任何超过 3 个配置项的项目。**何时不用**：只有一个 API_KEY 的脚本——`.env` + `os.getenv` 足够。

## 七、数据校验：Pydantic

**解决的问题**：外部数据（API 请求、JSON 文件、用户输入）不可信。你得验证类型、范围、格式——手写校验又长又容易漏。

**核心机制——声明式 Schema + 运行时强制转换：**

你声明一个模型类："name 是 str，age 是 0-150 之间的 int，email 是符合 email 格式的 str"。Pydantic 在实例化时自动校验，类型不匹配就尝试转换（`"25"` → `25`），转换不了就报错。

**Validator 链**：你可以挂自定义校验器——`@validator("age")` 在默认校验之后运行，做更复杂的业务规则检查（"age > 18 或 parent_consent 为 True"）。

**为什么比手写 if-else 强？** 手写校验有两个致命缺陷：①容易漏——每次新加字段可能忘记加校验 ②校验逻辑和数据结构耦合，改一个动全身。Pydantic 把 schema 定义就是校验——加字段=自动校验。

**设计洞察**："Trust boundary"（信任边界）是应用安全最重要的概念。你的代码应该在任何数据进入系统的地方放一个 Pydantic 模型——API 入口、文件读取、环境变量。过了这道门的数据就是可信的。

## 八、数据库迁移：Alembic

**解决的问题**：生产数据库不是开发数据库。加字段不能 `ALTER TABLE` 手动跑——你需要版本化、可回滚、可复现。

**核心机制——版本链 + autogenerate：**

每个 migration 是一个 Python 文件，包含 `upgrade()`（执行变更）和 `downgrade()`（回滚）。文件按版本号链式排列：`abc123 → def456 → ghi789...`。

`alembic revision --autogenerate` 对比你的 SQLAlchemy 模型和当前数据库的实际结构，自动生成 migration 脚本。你只需要 review、改改、提交。

**为什么 autogenerate 不是全自动？** 它只能检测"多了/少了一个字段"，但不能处理——①字段重命名（看起来像删了旧的加了新的）②数据迁移（把旧格式转成新格式）③复杂约束变更。所以 autogenerate 是起点不是终点。

**设计洞察**：Alembic 的设计哲学是"每个 migration 就是一个版本的数据库"。像 git 一样，你可以回到任意历史版本。这对生产环境至关重要——升级出问题，一个 `alembic downgrade -1` 回到上一版。

**何时用**：任何有持久化存储且会被部署的项目。**何时不用**：个人玩具项目，数据丢了不心疼。

## 九、连接池：SQLAlchemy Pool

**解决的问题**：创建数据库连接很昂贵（TCP 握手 + SSL 协商 + 认证）。每次请求新建连接 = 浪费 几十ms。

**核心机制——连接复用 + 空闲回收 + 溢出控制：**

连接池维护一组"活连接"。请求来了拿一个，用完还回去（不是关闭）。池空了怎么办？两种策略：①等待（QueuePool，默认）②创建更多但不超过上限。

**pool_pre_ping**：从池里拿出连接后，先发一条 `SELECT 1` 验证连接还活着。因为连接可能被服务端超时空闲关闭了。不开启 pre-ping → 拿到死连接 → 请求报错 → 用户体验差。

**idle 回收**：长时间不用的连接被回收，避免占用数据库的连接配额。

**溢出(max_overflow)**：连接池满后允许多创建几个临时连接。配合 `pool_size=5, max_overflow=10`，常态 5 个连接，高峰期最多 15 个，高峰过了回收。

**设计洞察**：连接池不是简单的"缓存 TCP 连接"。它是一套队列管理策略——等待 vs 创建、验证 vs 信任、固定 vs 弹性。这些决策直接影响服务在高负载下的表现。

## 十、缓存策略：cachetools / Redis / functools.lru_cache

**解决的问题**：同样的计算或者查询反复做——浪费 CPU、DB、网络。

**核心——缓存替换策略（淘汰算法）：**

这是缓存的灵魂。空间有限，满了要踢旧数据，但踢谁？

- **LRU（Least Recently Used）**：踢最久没被访问的。直觉："最近没人用的以后也不会用"。最通用。
- **TTL（Time To Live）**：每条数据设过期时间。直觉："这个数据 N 秒后就不可信了"。
- **LFU（Least Frequently Used）**：踢被访问次数最少的。直觉："冷门数据不值得缓存"。
- **FIFO（First In First Out）**：踢最早进来的。最简单但最不可靠。

**缓存三大陷阱：**

1. **缓存穿透**：查一个不存在的数据，每次穿透缓存打到 DB。解决：缓存空值 / 布隆过滤器。
2. **缓存击穿**：热点数据过期瞬间，大量请求同时打到 DB。解决：互斥锁——只让一个请求去重建缓存，其他等待。
3. **缓存雪崩**：大量缓存同时过期，DB 被压垮。解决：过期时间加随机偏移（± 30%）。

**设计洞察**：缓存不设上限 = 内存泄漏。缓存不设过期 = 数据永远不更新。选 LRU 还是 TTL 取决于数据特性——用户 session 用 TTL（安全要求），API 响应用 LRU（热数据自然淘汰）。

**functools.lru_cache 的应用**：Python 内置，装饰器一行搞定。适合纯函数（相同输入→相同输出），不适合有副作用的函数或需要分布式共享缓存。

## 十一、测试框架：pytest + hypothesis

**pytest 的核心——Fixture 依赖注入：**

传统 xUnit 模式：`setUp()` + `tearDown()` 在类级别。pytest 的 fixture 更灵活——函数级别的依赖注入。一个 fixture 可以依赖另一个 fixture，pytest 自动解析依赖链。

为什么这比 setUp/tearDown 强？因为 fixture 可以按需声明、可以参数化、可以在不同 scope（function/class/module/session）复用。你的测试函数只需要声明"我需要一个 db_connection"，pytest 自动注入。

**hypothesis 的核心理念——属性测试 (Property-Based Testing)：**

传统测试：你写输入，你写预期输出。问题：你只会写你能想到的输入。

Hypothesis：你描述"对所有输入应满足的性质"，Hypothesis 自动生成输入用例，尝试找出违反性质的最小反例。发现了反例后自动**缩小（Shrinking）**——"我找到了一个 1000 字节的字符串让测试失败，让我试试能不能用更短的复现...找到了，只要 3 个字符"。

**例**：传统的"测试 decode(encode(x)) == x"需要你手写一堆 x。Hypothesis 自动生成各种 x——空字符串、emoji、超长字符串、null 字节、RTL 字符...你没想到的它替你想到。

**设计洞察**：测试的本质不是"验证我写对了"而是"找到我写错的地方"。property-based testing 比用例测试更可能找到藏匿的 bug——因为它不依赖你的想象力。

## 十二、性能分析：py-spy / scalene / cProfile

**cProfile（标准库）——插桩式 (Instrumentation)**：在每个函数调用处插入计时代码。精确但有开销（10-30% 性能损失），不适合生产环境。

**py-spy——采样式 (Sampling)**：每隔 N 毫秒拍一张快照——"Python 解释器现在在哪行？"。开销极小（<2%），可以 attach 到正在运行的进程，不需要重启。

关键洞察：采样不是精确计时——一个运行 1μs 的函数如果永远不在采样时刻"中奖"，就完全看不见。但它能找到真正的热点——运行时间占比高的函数一定会被多次采样拍到。

**scalene——CPU + 内存 + GPU 三合一**：不仅测 CPU，还逐行跟踪内存分配（哪行代码分配了多少内存、之后释放了吗）。这对排查 Python 内存问题远比其他工具直观。

**火焰图 (Flame Graph)**：性能分析的最重要发明。横轴=时间占比，纵轴=调用栈深度。一个宽的"火焰"=耗时多的函数。颜色没有含义（随机），只为了视觉区分。

**设计洞察**：性能优化的第一原则——**先测量，再优化**。永远不要"觉得哪里慢"就优化。你直觉 80% 是错的。

**何时用**：系统上线前、用户反馈变慢了。**日常开发不需要**——premature optimization is the root of all evil。

## 十三、异步并发：asyncio 事件循环

**解决的问题**：IO 密集型任务（网络请求、文件读写）等待期间 CPU 完全空闲。同步代码里，等 = 阻塞 = 这个线程废了。

**核心——事件循环 (Event Loop)**

```
Event Loop = 一个无限循环，管理工作队列：
  1. 检查：哪些任务就绪了？
  2. 调度：从就绪的任务里选一个执行一小段
  3. 等待：没有就绪任务时，等 IO 事件唤醒
```

想象餐厅服务员：同步=一个服务员站在桌边等客人看完菜单，其他桌全晾着。异步=一个服务员同时照顾十桌——哪桌举手就去哪桌。

**协程(Coroutine) vs 线程(Thread)**：线程依赖操作系统调度（抢占式，随时可能切换），协程是协作式（主动 `await` 时才切换）。线程切换有开销（内核态），协程切换几乎零成本。

**关键陷阱**：`await` 才是"我让出控制权"。如果一个 async 函数里没有 `await`，它和同步函数一模一样——会阻塞整个事件循环。

**run_in_executor**：CPU 密集型操作不能放事件循环（真的需要算很久）。用 `run_in_executor` 扔到线程池/进程池——别阻塞主循环。

**设计洞察**：async/await 的价值不是让单一操作更快，而是让并发 IO 的吞吐量翻几十倍。100 个网络请求，同步=串行等，异步=同时发出去等。

**何时用**：IO 密集型、高并发的后端。**何时不用**：CPU 密集型、简单的 CLI 脚本。

## 选型速查

```
网络调外部 → tenacity(重试) + pybreaker(熔断)
             + httpx(超时控制) 三件套
慢操作异地 → RQ(简单) / arq(async) / Celery(企业)
日志可追踪 → loguru(开发) / structlog(生产→JSON)
配置管理   → pydantic-settings(>3配置项)
数据入口   → Pydantic(任何信任边界)
数据库结构 → Alembic(任何会被部署的DB)
DB连接     → SQLAlchemy Pool(任何Web服务)
缓存加速   → lru_cache(单进程) / Redis(多进程/分布式)
测试       → pytest(地基) + hypothesis(找隐藏bug)
性能定位   → py-spy(生产安全) / scalene(内存泄漏)
高并发IO   → asyncio(网络密集) / 线程池(CPU密集)
```

## 底层原理：这些工具内部是怎么工作的

### Redis 的数据结构：为什么它这么快

**Redis 快不只是因为"内存存储"——它的数据结构是精心设计的：**

- **SDS（Simple Dynamic String）**：Redis 的字符串实现。记录长度、预分配空间、二进制安全。比 C 字符串的 `\0` 结尾更高效——取长度 O(1)，拼接不反复分配内存。
- **Skip List（跳表）**：有序集合（ZSET）的底层。在有序链表上每 N 个节点建一层"快速通道"，查找从 O(n) 降到 O(log n)。**比平衡树简单得多**（不需要旋转调整），且天然支持范围查询。这就是"有序集合为什么快"的答案。
- **单线程 + 事件循环**：Redis 用单线程处理命令，通过 IO 多路复用（epoll）同时监听大量连接。**没有锁、没有上下文切换**——单线程反而让它扛住十万级 QPS。代价：单个慢命令会阻塞所有连接（`KEYS *` 就是这么危险）。

### SQLite：为什么它是全世界部署最多的数据库

**SQLite 的胜利靠三个设计决策：**

1. **无服务器（Serverless）**：不独立运行，作为库嵌进应用进程。没有端口、没有配置、没有运维。手机、浏览器、嵌入式设备都能跑。
2. **单文件存储**：整个数据库是一个文件。拷贝 = 备份，移动 = 迁移，发送 = 分享。这极其适合"数据要跟着用户走"的场景。
3. **WAL + 事务 + MVCC**：桌面级并发能力。读不阻塞写，写不阻塞读——对单机应用完全够用。

**权衡**：无服务器 = 没有网络访问（不能跨机器共享）、写并发受限（单写者）。**要跨机器/高并发写，才需要 PostgreSQL**——但在那之前，SQLite 是正确默认。

### 消息队列的 at-least-once：ack 机制怎么实现

**核心问题**：任务交给 Worker，Worker 处理一半崩了——任务会丢吗？

**ack（Acknowledgment）机制**：
1. Broker 把任务发给 Worker，任务标记为"处理中"（in-flight）
2. Worker 处理完**显式 ack**：告诉 Broker "我成功了"
3. 如果 Worker 崩溃没 ack → Broker 把任务**重新入队**给别的 Worker

**由此产生的保证**：
- **At-least-once**：任务绝不丢，但可能被处理多次（Worker 处理完了、ack 之前崩了 → 重新入队 → 又处理一次）
- **At-most-once**：不 ack，任务可能丢（Worker 拿到就删，崩了就没了）

**推论**：要可靠（at-least-once）就必须接受重复执行 → 处理函数必须幂等（见 01/02）。**ack 是可靠性的代价——它把"丢任务"变成"可能重复"，而重复靠幂等解决。**

### 连接池/线程池的调度：队列 + 信号量

**核心问题**：池里只有 N 个资源，第 N+1 个请求来了怎么办？

**通用机制**：
1. **队列**：请求排队等待空位（先进先出）
2. **信号量（Semaphore）**：一个计数器，取资源 -1，归还 +1，0 时新请求阻塞
3. **超时**：排队超过 X 秒 → 失败返回（不能无限等）

**关键决策点**：
- 队列满 / 信号量 0 → 等待（耐心）还是报错（快速失败）？——这就是检查单"到达上限后行为是等待/报错/扩容"的底层
- 长时间空闲的连接 → 回收（防占用配额）——`idle timeout`
- 池里的连接可能已死 → `pre_ping` 验证（见 04）

**洞察**：连接池、线程池、限流器、任务队列——全是同一个东西的不同变体：**有界资源 + 排队 + 超时**。理解一个，就理解了所有。

## 工程实践手段

| 原理 | 落地动作 |
|------|---------|
| Redis 数据结构 | 有序集合（ZSET）用跳表，千万级排序不卡；**绝不跑 `KEYS *`**（O(n) 阻塞单线程），用 `SCAN` |
| SQLite | 单机默认用 SQLite（WAL + busy_timeout）；要跨机器/高并发写才上 PostgreSQL |
| ack | 用任务队列（RQ/arq）时：处理函数幂等 + 失败重试有上限 + 死信队列 |
| 池化 | `pool_size` + `max_overflow` + `pre_ping` + 空闲回收，四件套 |
| 选型评估 | 一个库成熟度：活跃度/stars/bus factor/许可证/API 稳定/依赖数量，六项打分 |
| 换库成本 | 包装层（DIP）降换库成本——换库只动包装层，业务逻辑不动 |

## 同类替代对比：每个工具怎么选

> 上面讲了原理，这里给同一类工具的正面对比，帮你按场景定夺。

| 类别 | 选项 | 优劣一句话 |
|------|------|-----------|
| **重试** | tenacity vs backoff vs retry | tenacity 功能全（退避+jitter+谓词）成熟首选；backoff 极简装饰器；retry 轻量但少控制 |
| **熔断** | pybreaker vs circuitbreaker vs resilience4j | pybreaker 状态机清晰轻量；circuitbreaker 装饰器风格；resilience4j 功能最全（Java，含限流舱壁） |
| **日志** | loguru vs structlog vs stdlib logging | loguru 零配置开箱即用；structlog 数据/渲染分离适合生产 JSON；stdlib 功能够但样板多 |
| **数据校验** | Pydantic vs marshmallow vs dataclasses | Pydantic 类型强制+性能好；marshmallow 序列化灵活；dataclasses 标准库但无自动校验 |
| **任务队列** | RQ vs arq vs Celery vs Dramatiq | RQ 最简（enqueue 函数即用）；arq async 原生 at-least-once；Celery 企业级最全但最重；Dramatiq 平衡 |
| **HTTP 客户端** | httpx vs requests | httpx 支持 async+超时现代首选；requests 生态最老但同步 only |
| **缓存** | functools.lru_cache vs cachetools vs Redis | lru_cache 单进程一行接入；cachetools 多策略（TTL/LRU）；Redis 分布式共享 |
| **测试框架** | pytest vs unittest vs nose | pytest fixture 依赖注入是现代标准；unittest 标准库内置；nose 已弃用别选 |
| **性能剖析** | py-spy vs cProfile vs scalene vs line_profiler | py-spy 采样零侵入可上生产；cProfile 精确但开销大；scalene CPU+内存逐行；line_profiler 逐行最细但慢 |
| **配置管理** | pydantic-settings vs python-dotenv vs os.environ | pydantic-settings 声明+校验+优先级链一体；dotenv 只管加载 .env；os.environ 裸读无校验 |
| **日期时间** | zoneinfo vs pytz vs dateutil | zoneinfo 标准库（3.9+）零依赖首选；pytz 老牌但时区细节坑多；dateutil 解析人性化 |
| **进程守护** | systemd vs supervisord vs pm2 | systemd 系统原生最稳；supervisord 配置简单跨平台；pm2 Node 生态 |

**选型总原则**：功能相同先选**标准库**（零依赖）→ 再选**维护活跃 + 1.0+ + bus factor 高**的库 → 永远优先成熟而非花哨。跨语言项目记住：语言只是载体，模式（重试/熔断/池化/背压）是通用的。
