# 安全检查单

> 核心问题：你写的代码，被人利用了能造成多大伤害？
>
> 优先级说明：🔴 不做会丢数据/系统崩溃 | 🟡 不做有隐患 | 🟢 锦上添花

---

## 开工前（设计阶段）

- [ ] 🔴 **密钥管理**：API Key、密码存哪？硬编码？env？确认永不进 git。**不做的代价：密钥进 git = 永久泄露，即使删文件历史记录仍在。**
- [ ] 🔴 **输入校验**：用户输入校验了类型/长度/格式/范围吗？失败是拒绝还是清洗？
- [ ] 🔴 **SQL 注入**：100% 参数化查询（`?` 占位符）？有没有 f-string 拼 SQL？**不做的代价：整个数据库被拖走。**
- [ ] 🔴 **命令注入**：有没有用户输入传给 `os.system()` 或 `shell=True`？永远用参数列表替代
- [ ] 🔴 **路径遍历**：用户提供的文件路径是否校验在允许范围内？`../../etc/passwd` 防住了吗？
- [ ] 🔴 **敏感数据加密**：密码是哈希存储的吗（bcrypt/argon2，不是 SHA1/MD5）？能不能做到"DB 泄露也读不了"？
- [ ] 🔴 **最小权限**：这个服务需要什么权限就给什么，不需要 root 就别用 root
- [ ] 🔴 **Fail-Secure**：认证/鉴权服务挂了，默认行为是拒绝还是放行？**必须拒绝。不做的代价：认证服务宕机 = 所有人裸奔。**
- [ ] 🟡 **依赖审计**：`pip audit` / `npm audit` 跑过吗？有已知漏洞吗？
- [ ] 🟡 **HTTPS**：外部通信是否加密？证书有效？
- [ ] 🟡 **CSP（Content Security Policy）**：设置了 `Content-Security-Policy` header 吗？防 XSS 的最后一道防线。**不做的代价：即使你的代码没 XSS，依赖库的 XSS 也能执行。**
- [ ] 🟡 **Clickjacking 防护**：设置了 `X-Frame-Options: DENY` 吗？防止你的页面被嵌在恶意 iframe 里。
- [ ] 🟡 **安全 Headers 全套**：`HSTS`、`X-Content-Type-Options: nosniff`、`Referrer-Policy` 都配了吗？

## 上线前（验证阶段）

- [ ] 🔴 **git 历史扫密钥**：密钥从没进过 git 历史（push 就是永久泄露）
- [ ] 🔴 **注入测试**：输入 `'; DROP TABLE users; --` → 怎样？
- [ ] 🔴 **路径遍历测试**：输入 `../../../etc/passwd` → 能读吗？
- [ ] 🔴 **未授权访问测试**：不带 Token 能调 API 吗？
- [ ] 🔴 **Fail-Secure 测试**：停掉认证服务 → 请求被拒绝（正确）还是放行（错误）？
- [ ] 🟡 **超大输入测试**：输入 1MB 字符串 → 崩吗？
- [ ] 🟡 **安全 Headers 检查**：[securityheaders.com](https://securityheaders.com) 检测至少 B 级
- [ ] 🟡 **依赖漏洞扫描**：`pip-audit` / `npm audit` 无已知高危漏洞

## 每次提交前快速扫描

```bash
# 密钥进 git 了吗
grep -r "sk-\|api_key\|password" --include="*.py" --include="*.json" | grep -v ".git"

# SQL 拼接了吗
grep -rn "f\"\|f'" --include="*.py" | grep -i "select\|insert\|update\|delete"

# shell=True 了吗
grep -rn "shell=True" --include="*.py"

# 硬编码 URL/IP 了吗
grep -rn "localhost\|127.0.0.1\|192.168" --include="*.py" --include="*.json"
```

## 常见翻车

| 翻车现场 | 原因 | 怎么防 | 级别 |
|---------|------|--------|------|
| .env 进了 git | .gitignore 没加或加晚了 | 初始化项目第一步就加 .gitignore | 🔴 |
| SQL 注入 | 用户输入拼进 SQL | 只用参数化查询 | 🔴 |
| 认证宕机所有人能进 | fail-open 设计 | 认证/鉴权失败必须拒绝（fail-secure） | 🔴 |
| API Key 硬编码 | 图方便 | 只从环境变量读 | 🔴 |
| `shell=True` 注入 | 用户输入做命令参数 | 用 `subprocess.run([...])` 参数列表 | 🔴 |
| XSS 攻击（即使代码没问题） | 依赖库有 XSS，无 CSP 兜底 | 设置 Content-Security-Policy header | 🟡 |
| 页面被嵌入钓鱼 iframe | 无 X-Frame-Options | `X-Frame-Options: DENY` | 🟡 |
| 文件上传无校验 | 上传 .php → 被执行 | MIME 校验 + 扩展名白名单 + 存在非执行目录 | 🟡 |
| 日志泄露敏感信息 | Token/密码写进日志 | 日志输出前脱敏，确认日志文件权限 | 🟡 |
| 依赖库有已知漏洞 | 从不跑 audit | CI 中集成 `pip-audit`/`npm audit`，定期检查 | 🟡 |

## 反例（来自 MIND）

- ✅ SQL 全部参数化 — 好
- ✅ API 密钥从 env 读，config.json 不含密钥 — 好
- 🔴 `~/.claude/settings.json` 里 `ANTHROPIC_AUTH_TOKEN: "sk-b3c3e..."` 明文 — 本地风险
- 🟡 `_extract_project_slug()` 未校验路径格式 — 恶意构造可能绕过
- 🟡 看板无安全 Headers（CSP/X-Frame-Options/HSTS）— 依赖浏览器默认行为
- 🟡 无依赖审计 — 不知道 requests/Flask 等是否有已知漏洞

## 底层原理：被人利用了能造成多大伤害

### 信任边界：安全的第一性原理

**核心认知**：你的代码里存在一条隐形分界线——线外是不可信的外部世界，线内是你相信的代码逻辑。

```
不可信（线外）                信任边界               可信（线内）
用户输入 / API 请求  ──────  校验点  ──────  你的业务逻辑
网络数据 / 文件内容
环境变量 / 第三方返回
```

**关键实践**：每个数据入口放一个校验模型（Pydantic）——类型、长度、格式、范围全查一遍。**过了这道门的数据才可信**，内部逻辑不必再怀疑它。

**洞察**：检查单"用户输入校验"的底层逻辑——不是"防这一个输入"，而是"让线内代码永远面对可信数据"。信任边界画得越清晰，安全漏洞越少。

### 威胁建模 STRIDE：系统地找攻击面

**核心问题**：没有清单时，"哪里可能被攻击"全凭想象，想到哪算哪。

**STRIDE 是微软提出的六类威胁清单**：

| 字母 | 威胁 | 攻击者做什么 | 例 |
|------|------|-------------|-----|
| S | 仿冒 Spoofing | 假装是别人 | 伪造请求头、劫持会话 |
| T | 篡改 Tampering | 改数据 | 改请求参数、改日志 |
| R | 抵赖 Repudiation | 否认做过 | 无审计日志，事后赖账 |
| I | 信息泄露 Info Disclosure | 偷数据 | 目录遍历、日志泄密 |
| D | 拒绝服务 DoS | 拖垮系统 | 死循环请求、超大输入 |
| E | 提权 Elevation | 拿到更高权限 | 路径穿越拿 root 文件 |

**洞察**：检查单的每个安全条目几乎都能归到 STRIDE 某一类。遇到新功能，把 STRIDE 六项过一遍，比凭直觉找漏洞可靠得多。

### 哈希 vs 加密 vs 签名：三种完全不同的东西

**最容易混淆的三个概念**：

| | 哈希 Hash | 加密 Encryption | 签名 Signature |
|---|----------|----------------|---------------|
| 目标 | 验证完整性（没被改） | 保密（别人读不了） | 验证来源（确实是某人发的） |
| 可否逆 | 不可逆 | 可逆（有密钥） | 可验证 |
| 典型用途 | 密码存储、文件指纹 | 传输数据保密 | 防伪造、认证 |
| 例子 | SHA-256、bcrypt | AES、RSA | ECDSA、Ed25519 |

**关键区分**：
- **密码用哈希**（bcrypt/argon2）——不需要解出原密码，只需要"验证输入的密码哈希后对得上"。用加密存密码是大忌（能解出来 = 泄露）。
- **传输用加密**——保证路上没人偷看。
- **签名用于验证"是谁发的"**——JWT 的本质就是签名。

### 最小权限：只需要什么就给什么

**核心思路**：程序/用户/进程只获得完成任务所需的最小权限。DB 账号不给 DROP 权限，服务不用 root 跑，读接口不暴露写能力。

**为什么重要**：权限是攻击者拿到的"战利品"。权限越小，一次攻破的破坏半径越小。纵深防御的最后一道防线就是——即使代码被攻破，也做不了太多。

**洞察**：检查单"不需要 root 就别用 root"——底层就是最小权限。类比：门钥匙只给你房间的，不是大楼的万能钥匙。

### 纵深防御：每层都假设上一层会被攻破

**核心思路**：不依赖单一防线。即使 WAF 被绕过、输入校验被欺骗、认证被破解——下一层还在。

```
外层：WAF / 限流
中层：输入校验 / 参数化查询 / 安全 Headers
内层：最小权限 / 加密存储 / 审计日志
```

**洞察**：检查单同时要求"参数化查询 + CSP + 最小权限"——不是重复，是每一层防不同的突破点。安全界的铁律：**没有单一防护是够的**。

### 密钥的数学基础：熵与随机数

**核心问题**：为什么"长随机密钥"难猜？为什么密钥不该硬编码？

**熵（Entropy）**：衡量一个值"有多不可预测"。密钥的强度 = 熵 = 可能的取值数量。8 位数字 PIN 只有 1 亿种可能（约 26 位熵），暴力穷举秒破；256 位随机密钥有 2²⁵⁶ 种可能，穷举到宇宙热寂也猜不完。

**实践含义**：
- 密钥必须足够长且随机（高熵）
- 随机数必须是密码学安全的（`secrets` 模块，不是 `random`）
- 密钥硬编码进代码 = 熵瞬间归零（任何能读代码的人都知道）

**洞察**：检查单"密钥只从 env 读、永不进 git"——底层是保护熵。泄露的密钥 = 攻击者免费拿到了你的全部权限。

## 工程实践手段

| 原理 | 落地动作 |
|------|---------|
| 信任边界 | 每个数据入口（API/文件/env）放 Pydantic 模型，过了才可信 |
| STRIDE | 新功能过一遍六类威胁清单，每类至少想一个场景 |
| 哈希/加密/签名 | 密码用 bcrypt/argon2；传输用 TLS；JWT 用库签名，**绝不手写** |
| 最小权限 | DB 分账号（app 无 DROP）；服务不用 root；接口按需暴露 |
| 纵深防御 | 参数化查询 + CSP + Headers + 最小权限 多层叠加 |
| 密钥 | env 读取 + `.gitignore` + 定期轮换 + `git log` 扫历史 + `secrets` 生成 |
| 依赖 | pip-audit / npm audit 定期扫，CI 门禁 |
| 注入防御 | 参数化查询；`subprocess.run([...])` 不用 shell |

## 推荐开源项目（跨语言）

| 项目 | 语言 | 定位 | 优势 | 劣势 / 风险 | 适用场景 |
|------|------|------|------|------------|---------|
| **bcrypt** | C/多语言 | 密码哈希 | 自带 salt、抗彩虹表、久经验证 | 需调 cost 参数 | 密码存储 |
| **argon2-cffi** | C/Python | 密码哈希 | OWASP 推荐、抗 GPU 暴力、内存难并行 | 新一些、生态略小 | 新项目密码 |
| **libsodium / PyNaCl** | C/多语言 | 加密库 | 正确实现、侧信道防护、API 安全 | 概念门槛（无经验别自己组合） | 数据加密 |
| **PyJWT** | Python | JWT | 简单、生态好 | 只处理签名，密钥管理要自己做 | 认证 token |
| **python-jose** | Python | JWT 多算法 | 支持 JWK/RSA/EC | 更新慢于 PyJWT | 复杂 JWT 场景 |
| **Trivy** | Go | 依赖/镜像扫描 | 镜像+SBOM+文件系统、准、CI 友好 | 误报需人工甄别 | CI 漏洞门禁 |
| **pip-audit** | Python | PyPI 依赖审计 | 极简、离线缓存 | 只扫 Python | Python 依赖 |
| **npm audit** | Node | 依赖审计 | 内置、npm 生态 | 误报多 | Node 项目 |
| **OWASP ZAP** | Java | 主动安全测试 | 开源、主动扫描、可脚本化 | 重、需调教 | 上线前渗透测试 |
| **HashiCorp Vault** | Go | 密钥管理 | 集中管理、轮换、审计、动态凭证 | 运维复杂、重 | 生产多服务密钥 |

**选型建议**：密码一律 argon2 或 bcrypt（绝不 SHA/MD5）；加密用 libsodium 别手写；依赖扫描 pip-audit/npm audit 进 CI；密钥先从 env + .gitignore 开始，多服务了再上 Vault。
